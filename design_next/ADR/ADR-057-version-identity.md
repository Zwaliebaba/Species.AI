# Version identity: one generated build identity used by every consumer

## Context and Problem Statement

Many parts of Species need to know exactly which build is running: the executable's version resource, package manifests, the crash-report grouping and symbol store ([ADR-065](ADR-065-crash-reporting.md)), log headers ([ADR-067](ADR-067-logging.md)), telemetry ([ADR-066](ADR-066-telemetry-with-consent.md)), the save formats and the compatibility check between client and server (both designed in the design phase). If each consumer keeps its own number, they drift apart and a build cannot be identified from a crash report or a log.

How does a Species build identify itself?

## Decision Drivers

* One source of truth, generated by the build, never edited by hand in several places.
* The identity distinguishes code changes, content changes, products and configurations.
* Human-readable for players and support; exact for tools.

## Considered Options

* One generated build identity: semantic version, source revision, content hash, product and configuration
* Semantic version only
* Per-consumer version numbers

## Decision Outcome

Chosen option: "One generated build identity".

* **Fields:** a `MAJOR.MINOR.PATCH` semantic version (set in one checked-in file and changed by release changes only); a CI build number; the source-control revision id (with a "modified" marker for builds from a modified working tree); the content manifest hash of the content set built with it ([ADR-060](ADR-060-content-identity-by-hash.md)); the product and configuration (`Debug` or `Release`, [ADR-056](ADR-056-products-configurations-and-feature-flags.md)).
* **Generation:** a build step of the solution ([ADR-054](ADR-054-build-system-msbuild-solution.md)) generates one header, `BuildIdentityFields.h` (build output in `x64\<Configuration>\Generated\<Project>\`, never committed), with every field except the content manifest hash as constants, beside the hand-written `BuildIdentity.h` that declares the identity type, so that a content-only change never recompiles code; the packaging step writes one data file, `build_identity.json`, into the install directory with every field, the content manifest hash included. At start-up a program composes its full identity from the generated fields and the hash of the content manifest it mounts, and logs a mismatch with `build_identity.json` as a modified installation. The executable's `VERSIONINFO` resource (FileDescription, FileVersion, ProductName, ProductVersion), the package manifests ([ADR-072](ADR-072-distribution-channels-and-package-formats.md)), the crash black box, the log header and telemetry all read the generated values.
* **Display form:** `MAJOR.MINOR.PATCH+build.<number>`; the full identity, including revision and content hash, is shown in the options screen's build details and written at the top of every log.
* **Compatibility checks** between client and server, and between saves and builds, are defined by the design phase; they read this identity and never a separate number.

### Consequences

* Good, because every artefact of a build carries the same identity, so a crash report, a log and a package can be matched exactly.
* Good, because content-only changes are visible in the identity.
* Bad, because the version resource and package formats impose their own numeric formats, so the generator must map the identity onto each of them.

### Confirmation

* A CI step reads the version resource of every distributed PE file and the package manifest, and compares them with the generated identity.
* A unit test checks the mapping into each package format's version field.

## Pros and Cons of the Options

### One generated build identity

* Good, because it removes manual version edits from every consumer.
* Neutral, because it requires the CI build number and revision id at configure time.

### Semantic version only

* Bad, because two builds of the same version but different code or content would be indistinguishable in crash reports and logs.

### Per-consumer version numbers

* Bad, because they drift apart and cannot be reconciled after release.
