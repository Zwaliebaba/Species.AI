# Deferred decisions: process architecture, tick rate and build order

> Status: Decision register, deferred to the design phase · IDs: DEC-220 to DEC-229 · Related: [`reference/12_simulation_model/`](../../reference/12_simulation_model/README.md), [`decisions/deferred/networking.md`](networking.md), [`decisions/deferred/numerics_lobby_terrain_services.md`](numerics_lobby_terrain_services.md), [`adr/README.md`](../../adr/README.md)

## Scope

This file records three topics that the Species design phase decides: the process and threading architecture (how the client, the integrated server and the dedicated server are composed, who owns which state for how long, which threads run what, and how loops and loading are paced), the simulation tick rate with its per-tick budget, and the build order. The reference library specifies none of these as a Species architecture. It does specify, in `reference/12_simulation_model/`, the reference tick timing, the update slicing and per-tick update order, the player command catalogue, the generator discipline and the simulation-integrity rules. Those stay normative reference behaviour and are not reopened here: each entry states what the design phase must decide on top of them. The world context is the vision brief: a server-authoritative persistent world partitioned into regions, a server that starts integrated in the client and moves to dedicated headless hosts, and a match-based skirmish mode that runs on the same server path.

Every entry has the status **Open**. Its specified behaviour is the reference default. Two extra fields support the design work: **Constraints and lessons** lists, as numbered items, the integrity rules any Species architecture must respect, the hazards to avoid and the figures with their units; **Reference behaviour** describes the reference roles and properties in one paragraph. In both fields "must" is written in lower case, because these entries are not requirements; the design phase turns them into requirements when it decides.

## Process and threading architecture

### DEC-220 Process roles and the headless server build
- Status: Open
- Affects: the process structure of every Species build target; `architecture/components/platform_layer.md` (PLT), `architecture/components/build_tooling_and_distribution.md` (BLD), `architecture/components/diagnostics_test_and_performance.md` (DBG), `reference/12_simulation_model/01_tick_timing_and_main_loop.md` (R-SIM)
- Specified behaviour: The reference library specifies the simulation as rules and behaviour and defines no Species process roles. The reference default is one windowed client process that always contains the simulation and, on the host of a session, an in-process command sequencer. No headless build exists.
- Reference behaviour: The reference runs as one windowed client process. The host of a session, including a single player playing against bots, creates an in-process sequencer that it reaches over a loop-back connection; joining clients have none. The simulation advances only when the sequencer's updates are executed, so the network layer is the only source of simulation time, even offline. Once a session is hosted, the sequencer keeps ticking in the lobby and during loading. Solo and multiplayer play therefore share one code path and differ only in loop-back versus socket transport. The simulation cannot run without the window, the graphics device and the audio device.
- Constraints and lessons:
  1. One server codebase runs in-process (integrated) and stand-alone (dedicated) behind the same transport interface, and the client never touches server state directly (vision O10).
  2. The server builds and runs headless from day one: no window, graphics device or audio device, and no link dependency on renderer, audio, input or UI code (vision §5).
  3. The headless runner is also the main test vehicle: CI soak tests, server-side replay validation and bot-versus-bot matches run on it. A nightly soak covers every mode × map with bot teams and reports divergences, crashes, peak population and tick-cost percentiles.
  4. The skirmish mode runs on the same server path as the world (vision O8), so a match is always hosted by the integrated or a dedicated server, never by a client-only loop.
  5. The world is partitioned into regions from day one so that regions can later move to separate server processes (vision §5). A server process must be able to host one region, several regions, or one skirmish match.
  6. Community-hosted dedicated servers come first (vision O5). The vision brief recommends a Linux dedicated-server build for community hosts (vision §6 item 10), so server code must not depend on Windows-only client services.
  7. The settlement status and order interface is a server API (vision O6); it belongs to the server role, not to client logic.
  8. Lesson kept: one code path for solo and multiplayer play. Solo play is a client with an integrated server, exactly as a hosted session is.
  9. Lesson to avoid: an in-process server that is stepped from the client's frame loop runs slower when the host's frame is slow. The integrated server needs its own pacing, so that world time does not depend on the host's frame rate (DEC-225).
- Options: A — three build targets from one codebase: client, client with integrated server, and dedicated headless server; the server is a library with no presentation dependencies. B — one executable with run-time roles selected by a headless switch. C — a client-only process with the simulation embedded (the reference structure).
- Recommendation: A. Separate targets let the build enforce the dependency rule (the server library cannot link presentation code), keep the dedicated server small for community hosts, and make the integrated server literally the same library the dedicated server runs. B saves one target but turns the headless guarantee into a run-time convention that a stray include can break. C contradicts the server-authoritative constraint and the headless requirement.
- Decide by: design phase

### DEC-221 Composition root, service lifetimes and the application state machine
- Status: Open
- Affects: process start-up, shutdown and service ownership in every build target; `architecture/components/platform_layer.md` (PLT), `architecture/components/ui_framework/README.md` (UI), `architecture/components/audio_engine.md` (AEN), `reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md` (R-META), `reference/12_simulation_model/02_match_lifecycle_and_state_reset.md` (R-SIM)
- Specified behaviour: The reference library defines no process composition. The screen-level flow (front end, lobby, loading, match, results and return) is reference behaviour in `reference/09_front_end_and_match_flow/`. The reference default for composition is described below.
- Reference behaviour: One root object, created at start-up and reachable from everywhere, holds non-owning pointers to about thirty long-lived services, and about forty further process-wide mutable globals hold the rest of the process state. There are no service interfaces and no state machine: the program state is a set of independent flags (front end shown, lobby shown, requested match, loading in progress, game mode, editing, quit requested) that every loop consults. Construction has two phases: services that need the graphics thread are built on the main thread, and every other service is built on the loader thread while the main thread animates the loading view. The process ends only when a loop sees the quit flag; shutdown then deletes services in a fixed order and exits the process.
- Constraints and lessons:
  1. Every long-lived object belongs to exactly one lifetime class. The reference uses four: process (start-up to exit), session (one hosted or joined session, from lobby to end of match), match (one match world) and mode (re-created when the input-device class or the game mode changes). Species needs at least two more: world (one persistent world for the server's uptime, vision O4) and region.
  2. Ownership is explicit and unique, and no service is reached through a global. Lessons: pointer members that the first construction phase does not set stay indeterminate until the second phase assigns them; static queries are called before the root object exists.
  3. Construction and destruction follow one documented order, and each is the reverse of the other. Lesson: the reference destroys the window and graphics device before the services that own graphics resources, so those resources are abandoned rather than released.
  4. An object built on one thread and used on another is published through an explicit completion signal, never by writing a pointer that the other thread polls.
  5. Program state is one explicit state machine. The reference flow is boot → front end → lobby → loading → match → fade-out → teardown → front end, with quit reachable from the front end, from loading and from the match. Lesson: with independent flags, leaving a match needs two flags set together, and a stub loop survives for a flag combination that no match path produces.
  6. Quit is accepted from any loop, including mid-match, and every exit path runs the same teardown: end the match or detach from the world, send the leave notice, stop and join every thread, then release resources in order. Lessons: quitting mid-match leaks the match world, its input pump and the host's sequencer; the loader thread, the online-service threads and the host-side listener are never joined and end only with the process; one exit path (starting an external updater) leaves without any teardown.
  7. Every teardown wait is bounded. Lessons: the reference sends three leave messages and then blocks the main thread for 100 ms; one destructor busy-waits for an empty outbox without sending anything, which would hang if a message were still queued.
  8. Resource lifetime is explicit. Lesson: a replaced string table is deleted by a deferred job that runs on its sixth poll (one poll per main-loop iteration), so that windows still holding its phrases survive a few frames. Species needs handles whose validity can be checked (by generation or reference count), not frame-count delays.
  9. The simulation reads nothing from process-wide settings. Lesson: the reference simulation reads a process-wide difficulty level that is safe only because every level load forces it to 0.
  10. Foundation code uses standard containers, value types and one math library, and no service returns results through a shared static buffer. Lessons: the path helpers and the profile-directory query write into one static buffer each and are not re-entrant; two separate 3-vector types coexist.
  11. The client's composition root owns the integrated server's root (DEC-220) as a child with its own lifetime, so that stopping the integrated server freezes the world (vision O4) without tearing down the client.
- Options: A — one composition root per process role; services held by unique ownership in a documented construction order; lifetime scopes for process, session, world, region and match; one explicit application state machine. B — a service registry with lifetime scopes resolved at run time. C — the reference structure (one root object, globals, flags).
- Recommendation: A. A compile-time ownership graph makes the construction and destruction order visible, testable and reversible, and the lifetime scopes give every per-world and per-match object a single place where it is created and destroyed. B adds a flexibility the design does not need and hides dependencies again behind look-ups. Replacing the composition is a large, all-at-once change, so it belongs at the very start of the build (DEC-229), not in a later refactor.
- Decide by: design phase

### DEC-222 Simulation and presentation boundary
- Status: Open
- Affects: `reference/12_simulation_model/07_randomness_and_integrity.md` and `reference/12_simulation_model/01_tick_timing_and_main_loop.md` (R-SIM); `architecture/components/renderer/README.md` (RND), `architecture/components/audio_engine.md` (AEN), `architecture/components/ui_framework/README.md` (UI), `architecture/components/camera_and_sequences.md` (CAM), `architecture/components/build_tooling_and_distribution.md` (BLD); `decisions/deferred/networking.md`
- Specified behaviour: The integrity rules of `reference/12_simulation_model/07_randomness_and_integrity.md` apply: presentation never writes simulation state, all player intent enters the simulation as commands, and no presentation generator feeds the simulation. The reference presentation reads live simulation objects and extrapolates positions between ticks (`reference/12_simulation_model/01_tick_timing_and_main_loop.md`). The mechanism that enforces the rules in Species is open.
- Reference behaviour: Renderers, HUD, camera and audio read live simulation objects directly every frame. Positions are drawn extrapolated from the last tick as position plus velocity times the time since that tick, which snaps visibly when a direction changes. The simulation calls into HUD, camera and audio directly. The integrity rules hold by convention only: nothing in the build stops a presentation module from writing simulation memory, or the simulation from reading local presentation state.
- Constraints and lessons:
  1. The integrity rules are fixed and not reopened by this entry: presentation never writes simulation state; local-only state (camera, input mode, UI state) reaches the simulation only as a command; the presentation generator never feeds the simulation. The open question is how the architecture enforces them.
  2. Lessons: every live divergence path, and most latent ones, comes either from local or presentation state crossing into the simulation or from state that survives between matches (DEC-223). The crossing cases: Strike team direct control reads the local camera's look-around flag; tree hit spheres are drawn at load time from the shared presentation generator, which is not thread-safe and which an online-service thread also draws from; some renderers write simulated fields, which DEC-007 forbids: the Supply crate orientation and bubble timer, once per rendered frame; a thrown weapon's orientation, tumble and flash count, and its flash sound; the shell-casing facing that its advance reads; the Barrier Emitter link, which its renderer marks as absent when the linked id is missing or names no Barrier Emitter, for emitters in view only (Species validates links at build, DEC-015, and the simulation treats a missing link as absent); the Beam Dish range and receiver, which its renderer saves and restores around link drawing; a Solar Array's orientation from the terrain normal, equal to the value its initialisation sets; and a turret's facing, in the editor only. The world cursor's crosshair assigns, instead of comparing, the structure kind of the local team's selected structure, which is dormant because only the Beam Dish and turrets can be selected; the simulation reads a process-wide difficulty level, harmless only because every level load forces it to 0 (DEC-221 item 9).
  3. Enforcement is structural: the simulation library cannot include camera, input, UI, audio or renderer interfaces (a module boundary or an include allow-list), and the build fails on a forbidden include.
  4. A conformance test runs the simulation headless with presentation stubs and compares its per-tick state hashes with those of a full client running the same inputs.
  5. The simulation emits typed events (for example hits, deaths, Essence orb releases and sound cues) into a per-tick queue that presentation and audio consume on their own threads. The queue contract states what is guaranteed and what may be dropped. Lesson: the reference audio engine silently drops a sound trigger made from a non-main thread, during a loading view, or before the sound archives are loaded.
  6. Renderers receive read-only snapshots. If Species interpolates between the previous and the current tick, the fixed display delay is one tick: 100 ms at the reference rate of 10 Hz (`ref.sim.tick_period`), 50 ms at 20 Hz and 33 ms at 30 Hz (DEC-227).
  7. Visual effects stay entirely outside the simulation: particles, debris and other cosmetic effects never change a simulation outcome. These cosmetic draws move from the simulation stream to the presentation generator (DEC-013): the ant leg shape (every tick per ant), snowflake and Wisp wobble (four draws per object per tick), meteor fire size (five per tick), Spitter Plant fire size, turret shell casings (four per shot) and overheat smoke, Trooper casings, the Worker abduction spark and the volcano vent idle draw. Only the draws move: the decorative objects themselves (snowflakes, Wisps, muzzle flashes and shell casings) stay in the simulated effect pool and take object serials, and whether they leave it is DEC-266; the hover draws of Essence orbs stay simulation draws, because an orb's position is simulation state. Spider leg and foot state, with its wall-clock swing timing, is presentation only (DEC-007).
  8. In Species this boundary is also the network boundary. A client renders the replicated state it is allowed to see, and fog of war applies equally to players, bots and the deputy (vision §5), so the snapshot format and the replication format are best designed together (`decisions/deferred/networking.md`).
- Options: A — a strict one-way boundary: the simulation publishes an immutable per-tick snapshot and a typed event queue, presentation reads only those, and the build enforces it. B — a shared object graph with read-only views for presentation, enforced by const access and review. C — the reference model (direct access, convention only).
- Recommendation: A, with interpolation from the last two snapshots. A snapshot is needed anyway to replicate state to remote clients and to interpolate; making it the only presentation input lets the integrated server and a remote dedicated server look identical to the client (vision O10) and turns each known divergence path into a build error rather than a runtime fault. B is cheaper inside one process but cannot serve remote clients, so Species would need A as well.
- Decide by: design phase

### DEC-223 World, region and match state ownership and reset
- Status: Open
- Affects: `reference/12_simulation_model/02_match_lifecycle_and_state_reset.md`, `reference/12_simulation_model/03_entity_model_and_identity.md`, `reference/12_simulation_model/07_randomness_and_integrity.md` (R-SIM); `architecture/components/data_schemas/README.md` (DAT); `decisions/deferred/numerics_lobby_terrain_services.md` (persistence)
- Specified behaviour: Per-match state is owned and reset when a match starts; this is a reference integrity rule, and the reference reset points are specified in `reference/12_simulation_model/02_match_lifecycle_and_state_reset.md`. Which Species object owns world, region and match state, and how that state is created, saved and destroyed, is open.
- Reference behaviour: One match world object (`MatchWorld`) holds the map, teams, objects and grids of a match and is created for each match. Much simulation-relevant state lives outside it: about forty class-static and file-static variables are reset by hand at match initialisation, with gaps; the match rules object and the tick clock are process-lifetime objects reset at defined points; the simulation generator is seeded when a client joins a session, not per match; the presentation generator is re-seeded with the value 1 at each match initialisation; the object unique-id seed is reset at each match load. Every match uses the same fixed match id.
- Constraints and lessons:
  1. Integrity rule, fixed: no simulation state survives from one match into the next.
  2. Lessons, state that survives between matches: a process-wide count of Control Zones used by the zone-scoring pass (a reachable divergence); a per-team Spawn Node count for the sixth team slot (latent); a Transport direct-orders debounce (latent, because nothing sends that command); the teleport structures' transit table, which is pruned only when its unit no longer exists and has no per-match clear; tick-clock fields that are not all reset, so the speed state can drift across matches to negative infinity or not-a-number.
  3. One owner holds every mutable simulation value: ids and id seeds, counters, timers, bot tables, generator state and caches, so that a match or a region is created and destroyed atomically. Mutable statics in simulation code are forbidden and checked by static analysis; shared static scratch buffers (for example a neighbour list reused by every query) become per-call or per-thread.
  4. Conformance test: play match A and then match B in one process, and match B alone in a fresh process; the per-tick state hashes of B must be identical.
  5. Species runs several owners in one process: several regions on one server, and a skirmish match beside the world on an integrated server. Any process-wide simulation state breaks this, so the Species rule is stricter than a reset at match start: nothing simulation-relevant exists outside an owner.
  6. A persistent world never resets. Its owners live for the server's uptime, freeze while the server is down (vision O4) and are saved to and loaded from a database (vision O1). The owner is therefore the unit of persistence and must serialise without hidden state; the persistence format is decided with `decisions/deferred/numerics_lobby_terrain_services.md`.
  7. Identity survives persistence and region hand-over: one 64-bit generational handle per pool (32-bit index, 32-bit generation), checked on every dereference for every object kind, including Essence orbs and projectiles (`reference/12_simulation_model/03_entity_model_and_identity.md`). A per-match id-seed reset cannot apply to a world that never restarts.
  8. Battles always run the full simulation, while the economy of settlements nobody is watching runs an abstract model (vision O3). The owner design must let a region switch between the two representations without carrying hidden state across the switch.
  9. Every generator stream belongs to an owner and is seeded from the owner's data, never from a session join (`reference/12_simulation_model/07_randomness_and_integrity.md`).
- Options: A — one state owner per region and one per skirmish match, holding every mutable simulation value, with no simulation statics anywhere. B — a per-region entity registry (a component store) plus per-region system state, under the same rules. C — the reference model (a match object plus hand-reset statics and process-lifetime rule and clock objects).
- Recommendation: A, with B as an implementation choice inside it. A single owner per region or match is what makes atomic creation and destruction, the match-after-match hash test, persistence and region hand-over possible; whether the owner stores objects in typed pools or in a component store does not change those properties. C keeps the failure modes listed in item 2.
- Decide by: design phase

### DEC-224 Threading and job model
- Status: Open
- Affects: `reference/12_simulation_model/04_containers_and_update_order.md` and `reference/12_simulation_model/07_randomness_and_integrity.md` (R-SIM); `architecture/components/platform_layer.md` (PLT), `architecture/components/renderer/README.md` (RND), `architecture/components/audio_engine.md` (AEN), `architecture/components/asset_pipeline_and_resources.md` (AST), `architecture/components/diagnostics_test_and_performance.md` (DBG); `decisions/deferred/numerics_lobby_terrain_services.md` (numeric model)
- Specified behaviour: The reference per-tick update order and update slicing in `reference/12_simulation_model/04_containers_and_update_order.md` describe single-threaded behaviour: at any moment at most one thread runs simulation code. The Species threading model is open.
- Reference behaviour: All game work runs on the main thread: input, the network pump and every network send, command sequencing, the whole simulation, rendering, sound logic and audio mixing. The process creates ten kinds of thread: the main thread, a loader thread, a sound-loader thread, a client-side and a host-side network listener, and five online-service kinds (a listener, authentication, a wide-area and a local-network registration thread, and one identity-request thread per identified listener); the operating system's audio callback runs on one more thread. Workers only load data and receive packets; listeners only enqueue, and the main thread interprets everything. Only the main thread and the loader thread (during a level load) run simulation code, and never at the same time. Each worker serves a strictly serial first-in-first-out queue, and a worker that needs the graphics device blocks until the main thread has run its request.
- Constraints and lessons:
  1. Any parallelism inside the simulation keeps the outcome independent of thread count and scheduling: phases read the previous state and write per-object outputs, reductions run in a fixed order, each job or object draws from its own generator sub-stream, and no mutable cache is shared between jobs. A parallel loop over steps that share mutable state breaks this.
  2. The reference per-tick update order is part of the rules. A parallel design either reproduces its observable order or adopts a new order explicitly; in both cases the order of rule evaluation within a tick is specified.
  3. A level load draws from the simulation generator; a concurrent or streamed loader keeps that draw order fixed.
  4. The numeric environment is identical on every thread that runs simulation arithmetic. Lesson: the reference sets its floating-point mode per thread, on the main thread and the queue threads only; listener and service threads run with the default mode and are safe only because they do no simulation arithmetic (`decisions/deferred/numerics_lobby_terrain_services.md`).
  5. Scheduling is sized to the hardware, with no fixed affinity masks. Lesson: the reference masks assume at most 8 logical CPUs, pin the main thread to odd-numbered CPUs and the workers to even-numbered ones.
  6. Every thread has an owner that stops and joins it. Lessons: thread handles are neither kept nor closed, and only queue destructors join their thread; one thread entry point is cast to the platform's thread signature with a mismatched calling convention and works only because it returns solely at shutdown.
  7. Cross-thread publication uses atomics or locks with a defined memory order. Lessons: a sounds-loaded flag is a plain boolean; objects built on the loader thread are read by the main thread's loading loop while their construction is still running; an audio buffer counter is incremented by the audio callback thread and decremented by the main thread without synchronisation, so updates can be lost and a buffer starved or over-filled; a loading-view flag is uninitialised until its first use although other threads can query it.
  8. An object that a listener calls outlives the listener: the listener is stopped and joined before the object is destroyed. Lesson: the host-side listener reads its target object without a lock and can deliver a packet into an object that is being destroyed.
  9. No generator is shared between threads. The integrity rule covers the simulation generator; the lesson is that an online-service thread draws from the shared presentation generator concurrently with the main thread.
  10. Shared caches are safe for concurrent use by contract, not by timing. Lessons: texture look-ups take the asset-cache lock only while a loading view is shown, which is safe only because no worker uploads at other times; container read accessors move a cached cursor, so even reads need the lock; the archive decompressor is not thread-safe, so the two loader threads are kept apart only by start-up order.
  11. No graphics work is handed to one thread through a blocking request. Species records command lists on several threads and uploads through the copy queue (`architecture/components/renderer/README.md`), which removes the reference's deadlock rule that the main thread must be inside a request-draining loop whenever a worker can issue a graphics request (the front-end loop does not drain them).
  12. Network I/O runs on dedicated threads that hand data to its owner through lock-free queues; audio mixing runs on the audio API's own callback thread, which touches only the data the audio engine hands it through its queues, and the callback contract states that no other audio-system thread touches game memory (`architecture/components/audio_engine.md`); logging is asynchronous and buffered on its own thread, with per-category levels, and never opens and closes a file per line.
  13. On a server, the step of one region runs independently of other regions, so regions can run on separate threads now and in separate processes later (vision §5). The integrated server's threads exchange data with the client only through the transport (vision O10).
- Options: A — one simulation thread per region or match, with a deterministic job system for the heavy phases inside a step (searches, grids, routing); presentation, network I/O, audio, streaming and logging on their own threads. B — a fully parallel per-tick job graph across all simulation systems. C — the reference model (all game work on one thread).
- Recommendation: A. One simulation thread per region keeps the reference update order easy to reproduce and test, while the job system parallelises the hot spots and the region split scales across cores and later across processes. B can reach higher throughput but makes order-dependent rules hard to keep and to verify. Whatever determinism level the numeric-model and networking decisions choose, a step should at least be reproducible from the same state and inputs on the same build, because replay validation, soak tests and the calibration of the abstract economy model against the full simulation (vision O3) depend on it.
- Decide by: design phase

### DEC-225 Frame loop, simulation pacing and catch-up
- Status: Open
- Affects: `reference/12_simulation_model/01_tick_timing_and_main_loop.md` (R-SIM), `reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md` (R-META), `architecture/components/platform_layer.md` (PLT), `architecture/components/diagnostics_test_and_performance.md` (DBG)
- Specified behaviour: The reference tick timing, update slicing, slice scheduling, catch-up rules and frame advance clamp are reference behaviour in `reference/12_simulation_model/01_tick_timing_and_main_loop.md`. How Species paces its server ticks, its client frames and catch-up is open. What keeps running while game speed is 0, and how the fraction of a tick is carried, is DEC-264.
- Reference behaviour: Every loop is a busy loop on the main thread that never sleeps or yields, except the loading loop. An outer loop dispatches to the front-end loop (menus and lobby) or the match loop, and both run common checks on every iteration (quit, window focus, one deferred job, controller loss, memory log, audio-device start-up); the loading loop is entered at start-up and for each match load. The host's sequencer issues one update every 0.1 s of real time, and each client executes it as 10 update slices spread over its render frames, scheduling about 30 % of the slice backlog per frame; there is no other source of simulation time. The lobby runs the same 10 Hz tick, and lobby commands are sequenced updates exactly like match commands. The frame advance time is clamped to at most 0.25 s and does not change while paused. Pause is a game speed of zero inside the tick clock.
- Constraints and lessons:
  1. Simulation time has one explicit source, the server's tick clock, counted in integer ticks. The step function depends on no networking, UI or rendering code.
  2. The client frame and the server tick are decoupled: the client renders at its own rate from snapshots (DEC-222) and never steps the authoritative simulation.
  3. Catch-up is bounded in ticks per frame and visible to the player. Lessons: after a load the reference replays buffered updates at 20 slices per loop iteration with at most 0.3 s of simulation per frame, so a slow client spends more of each frame simulating and its frame rate falls further (a catch-up spiral); and the slice scheduler has a dead band in which 1 to 3 pending slices advance nothing. Species shows a catching-up state instead of letting the frame rate collapse.
  4. The server keeps ticking while a client loads, and the loading client keeps its connection alive. Reference figures: the host keeps its 10 Hz tick through every load, and a loading client sends a keep-alive at most once per 1.0 s. In Species no client load ever pauses a region.
  5. A persistent world has no pause: world time stops only while the server is stopped (vision O4). Where a skirmish allows pause, it is a sequenced command with an immediate effect, not a game speed of zero blended inside the clock; speed effects are deterministic tick scheduling.
  6. No loop busy-waits. Client frames are paced by the swap chain's present interval (`architecture/components/platform_layer.md`), and the server tick loop sleeps until its next deadline.
  7. A lobby or pre-match phase is a state of the server's state machine, not a reduced simulation tick; the lobby protocol is decided with `decisions/deferred/numerics_lobby_terrain_services.md`.
  8. One monotonic clock with an injectable fake clock serves capture and replay (`architecture/components/platform_layer.md`).
  9. The window message pump belongs to the platform layer and runs once per frame, not inside the input update.
  10. Frame budget: the reference renders as fast as it can, with no sleep in the match loop; clamps the presentation frame delta to 0.25 s; advances audio a second time after rendering when the frame rate is below 15; writes a memory report to the log every 60 s; pins its main thread to four alternate cores; and marks 50, 100 and 200 ms per frame on its profiler graph. Of these, only the 0.25 s presentation clamp has a Species counterpart to state (ADR-0012).
- Options: A — a fixed-rate server tick loop that sleeps to its deadline, plus a variable-rate client frame loop with snapshot interpolation and bounded, visible catch-up, for both the integrated and the dedicated server. B — client-driven stepping for the integrated server (the client frame calls the server step) and A for the dedicated server. C — the reference model (sequencer updates spread over frames as slices).
- Recommendation: A. The integrated server runs its tick loop on its own thread, so the host's frame rate never changes world time and the integrated and dedicated servers behave identically, which the single-codebase constraint (vision O10) needs. B is simpler for the first playable but makes world time depend on the host's frame rate and gives the integrated server a second pacing path to test.
- Decide by: design phase

### DEC-226 Loading, streaming and asynchronous work
- Status: Open
- Affects: `architecture/components/asset_pipeline_and_resources.md` (AST), `architecture/components/renderer/README.md` (RND), `architecture/components/audio_engine.md` (AEN), `architecture/components/terrain.md` (TER), `reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md` (R-META); `decisions/deferred/numerics_lobby_terrain_services.md` (terrain runtime model)
- Specified behaviour: The loading view's visuals and its place in the screen flow are reference behaviour in `reference/09_front_end_and_match_flow/`. Asynchronous loading on the client is engine scope in the asset pipeline component. How the Species server and client load and stream world content is open.
- Reference behaviour: Boot work and each match load run on one first-in-first-out loader thread while the main thread runs a blocking loading loop capped at 60 Hz. Each loading frame pumps window messages without advancing input, draws the loading view, keeps the network alive if it can take the network lock without waiting, and runs queued graphics requests from the worker until the 1/60 s frame deadline. The loop ends when the worker is idle, no graphics request is pending, the sounds are loaded where required and, on the initial load, the 1.0 s logo fade is complete. Sound archives load on a second thread once boot work has finished; the audio device opens on the first front-end iteration, usually before the sounds are loaded, and game sounds are dropped until then. The main thread learns that a load has finished only by seeing the worker idle. There is no progress reporting.
- Constraints and lessons:
  1. The network stays alive and the server keeps ticking during every load (DEC-225 item 4).
  2. Completion and results are signalled explicitly (a completion event or future), never inferred from an idle queue with the results published through shared pointers.
  3. Loads report progress.
  4. GPU uploads go through the copy queue with batched I/O, and no loader thread ever blocks on the presentation thread (DEC-224 item 11).
  5. Content readers are safe for concurrent reads (`architecture/components/asset_pipeline_and_resources.md` and the pack-file ADR in `adr/`). Lesson: the reference archive decompressor is not thread-safe, and the two loaders are kept apart only by start-up order.
  6. Audio readiness is a defined state: the audio device and the sound banks each have a ready point, and what happens to a cue issued before it (dropped or deferred) is specified.
  7. A level load that draws from the simulation generator keeps a fixed draw order (DEC-224 item 3).
  8. A large persistent world streams terrain and content and never loads the whole world (vision §6 item 6). The server never blocks a region's tick while it loads another region, and a region hand-over loads ahead of need. Whether terrain is generated at load or baked is decided with `decisions/deferred/numerics_lobby_terrain_services.md`.
  9. Previews that the reference loads under a loading view only to keep the asset cache safe (map thumbnails) load in the background in Species, because the cache is safe for concurrent use by contract (DEC-224 item 10).
- Options: A — streaming everywhere on the job system with progress reporting; skirmish and world entry show a short loading view only until the first visible set of content is resident. B — a blocking loading view for each skirmish match and for world entry, with streaming only during play. C — the reference model (one serial loader and a blocking loading loop with no progress).
- Recommendation: A for the persistent world, which cannot be loaded as a whole; B is acceptable for the skirmish if it shortens the path to the first playable, because a skirmish map is small. Both keep the server ticking and the connection alive during a load, and both need explicit completion signals and concurrency-safe readers.
- Decide by: design phase

## Tick rate and per-tick budget

### DEC-227 Simulation tick rate
- Status: Open
- Affects: `reference/12_simulation_model/01_tick_timing_and_main_loop.md` and `reference/12_simulation_model/04_containers_and_update_order.md` (R-SIM); every reference tuning table that holds tick-denominated values (R-MODE, R-UNIT, R-BLDG, R-CRATE, R-ECON, R-CTRL, R-BOT, R-AUD, R-TUT); `decisions/deferred/networking.md`
- Specified behaviour: The reference tick rate is 10 Hz: one tick every 0.1 s (`ref.sim.tick_period`, `kTickPeriod`), each tick executed as 10 update slices (`kUpdateSlicesPerTick`). Every reference duration is stated in ticks at that rate. The Species tick rate is open, and the reference rate is the default.
- Reference behaviour: The reference advances a fixed 10 Hz tick in real time, and game time advances by 0.1 s × game speed per tick in floating-point accumulators. Work inside a tick is spread over 10 update slices whose bounds come from pool capacity, and the match rules update runs in slice 8 (counting from 0). Rendering extrapolates object positions between ticks.
- Constraints and lessons:
  1. The clock counts whole ticks as integers. Speed effects are deterministic tick scheduling or a fixed-point time step, and every timer field resets with its owner (DEC-223).
  2. A change of tick rate rescales every tick-denominated value in the reference tuning tables: durations, per-tick rates, cool-downs, stagger periods and mode timers, including the mode second of 11 ticks. The design phase decides whether Species keeps the reference values in ticks (so the game runs faster in real time) or converts them to keep the reference real-time behaviour, and fixes one rounding rule for the conversion.
  3. 10 Hz is coarse for a current real-time strategy feel; 20–30 Hz is the usual range.
  4. Update slicing exists only to spread single-threaded cost over frames; a Species step runs whole ticks (DEC-224). Where slice placement changes an outcome (which objects update in which slice; the rules update in a fixed slice), the observable order is re-expressed in tick order (`reference/12_simulation_model/04_containers_and_update_order.md`).
  5. With interpolation the display delay is one tick: 100 ms at 10 Hz, 50 ms at 20 Hz and 33 ms at 30 Hz (DEC-222).
  6. The tick rate multiplies the server CPU cost per region and the replication bandwidth per client (vision §6 items 4 and 5), and it sets the command and snapshot cadence of the networking model (`decisions/deferred/networking.md`).
  7. The full simulation and the abstract economy model need not share a rate (vision O3): a battle region and an unwatched region may tick at different rates if the hand-over between them is exact.
  8. The rate is fixed by measurement, not by assumption: no measured frame times or tick costs exist for the reference, so a prototype measures the tick cost at the population cap (DEC-228) before the rate is final.
- Options: A — keep 10 Hz. B — 20 Hz. C — 30 Hz. D — 20 or 30 Hz for the full simulation (battles and watched regions) and a lower rate for the abstract economy model.
- Recommendation: D, with 20 Hz as the working value for the full simulation. Compared with 10 Hz it halves the display delay and the command latency, it doubles rather than triples the server cost, and it divides a 60 Hz frame rate evenly (three frames per tick). A lower rate for the abstract model keeps unwatched settlements cheap. The value is confirmed by the prototype measurement of item 8; Species tuning is stated in ticks of the chosen rate, converted from the reference by the single rounding rule of item 2.
- Decide by: design phase

### DEC-228 Per-tick CPU budget, population caps and stress populations
- Status: Open
- Affects: `architecture/components/diagnostics_test_and_performance.md` (DBG), `architecture/components/renderer/options_and_budgets.md` (RND), `reference/05_population_flow.md` (R-ECON), `reference/12_simulation_model/05_space_routing_and_physics.md` (R-SIM), `reference/01_skirmish_rules_and_modes/README.md` (R-MODE)
- Specified behaviour: The reference population limits and spawn economy are reference behaviour in `reference/05_population_flow.md` and the mode documents. The reference defines no CPU budget and no hard engine population limit. Species budgets and caps are open.
- Reference behaviour: The reference has no per-tick budget; population is limited by map and mode options, not by the engine. A busy map peaks at about 2,000 units plus Essence orbs and laser bolts. Target searches are staggered over 1–2 s, and spatial queries use approximate per-cell counts with a 1 s cache. No measured frame times or tick costs exist.
- Constraints and lessons:
  1. A hard per-tick CPU budget applies at the population cap on minimum-spec hardware, split into per-system budgets. Reference guidance: at most 25 % of a 16.7 ms frame, about 4.2 ms. The design phase states whether the figure is the cost of a whole tick or a per-frame share amortised over the frames of a tick; when a whole tick runs at once, the frame that carries it carries its whole cost.
  2. Design population: the reference peak of 2,000 units per map plus Essence orbs and projectiles. Stress population: twice that (4,000 units), tested on an uncapped stress map with 4 teams × 150 starting units and 24 Spawn Nodes.
  3. The population cap is a hard engine limit, not only a map option.
  4. Searches keep the 1–2 s stagger, but spatial queries are exact (no cache shortcut that changes a result) and data-oriented (structure of arrays, SIMD over cell lists), with a query budget per tick. If approximate counts are wanted as gameplay, they are specified as rules.
  5. Particles and other visual effects use fixed-capacity pools with a hard cap and graceful level of detail, outside the simulation (DEC-222). Units are drawn instanced (one draw per unit type per pass) within a per-frame draw-call budget (`architecture/components/renderer/options_and_budgets.md`).
  6. Client target: a local Spawn Control match at 60 fps with 2,000 units on minimum-spec hardware. With an integrated server (vision O10), the server tick and the client frame share that machine, so the integrated case fits both inside the frame.
  7. Server target: the cost per settlement and per battle at 16 and at 200 players, with explicit population and battle-size limits (vision §6 item 4). Community-hosted servers come first (vision O5), so the budget is stated for a named community-host specification.
  8. Measurement precedes commitment: the first simulation-core milestone measures tick cost (DEC-229), and the nightly soak reports tick-cost percentiles and peak population (DEC-220 item 3).
  9. Diagnostics stay out of the budget: logging is asynchronous and buffered (DEC-224 item 12).
- Options: A — a client-derived budget (at most 25 % of a 16.7 ms frame per tick at 2,000 units on minimum spec), with the server budget per region derived from it. B — a server-first budget (fixed milliseconds per region tick on a stated community-host specification), with the client budget derived from it. C — no hard budget, with population limited dynamically by measured cost.
- Recommendation: A and B together. The client budget protects the skirmish and the integrated server on minimum-spec machines; the server budget protects community hosts and sets the per-region population and battle-size limits that the 16-to-200-player path needs. Both are hard limits enforced by the engine cap and verified by the stress population of item 2. C makes battle outcomes depend on host hardware and is unsuitable for a shared world.
- Decide by: design phase

## Build order

### DEC-229 Build order, milestones and work breakdown
- Status: Open
- Affects: the Species roadmap; every reference document and engine component as a work item; `assets/README.md` (placeholder strategy)
- Specified behaviour: The reference library defines no build order. The reference work breakdown below is an input to the Species plan; the order itself is the design phase's.
- Reference behaviour: The reference work breakdown has nine work packages, from decisions and foundations to production. It builds the simulation core first, then a headless gameplay slice through one mode, then client presentation, networking, content breadth, tools, the front end with platform services, and production. Each package has deliverables, dependencies and an exit check, and eight workstreams run across them.
- Constraints and lessons:
  1. Core first: the simulation core, its tests (replay hashing) and the headless runner come before any rendering, and every later system is built inside or against them. In Species this core is the headless server core (DEC-220).
  2. The composition and state-ownership structure (DEC-221, DEC-223) is built at the start; changing it later is a large, all-at-once refactor.
  3. Decisions before tuning: Open decisions that change rules are settled before the reference values are adopted as the tuning baseline (vision O13 allows that adoption).
  4. Placeholders everywhere: procedural placeholder art and audio named by role (`assets/README.md`) let engineering finish before final assets exist.
  5. A vertical slice through one mode: Spawn Control exercises the economy, crowds, Leaders, combat and Essence orbs without mode-specific objects, so it is the reference first playable. In Species the skirmish is the first playable and the combat balance test bed, and it runs on the in-process server (vision O8, O10). The owner fixed the first playable as Spawn Control with 2 players and the core Supply crate pool (vision O20).
  6. Dependency constraints of the reference work breakdown (contents; what each package needs; its exit check):
     - Foundations. Contents: the numeric model, the tick rate, the rule-changing decisions, the platform choice, repository, CI, coding rules (no statics in simulation code, a generator lint, an include allow-list) and a content-schema skeleton. Needs: nothing. Exit check: CI builds an empty simulation library with the forbidden-include and static checks active.
     - Simulation core. Contents: the state owner, the step function, the deterministic math library, the simulation generator, object pools with generational handles, per-team spatial grids, the obstruction grid, the baked-heightfield loader and terrain queries, the command format, the state hash, the replay recorder, the headless runner and the job system. Needs: Foundations. Exit check: a synthetic 2,000-unit match replays with identical per-tick hashes on two Intel and two AMD machines, and the tick cost is measured.
     - Headless core gameplay. Contents: Worker behaviour and combat, Essence orbs, the spawn network and economy, Leaders and formations, selection and order commands, the match-rules skeleton with Spawn Control, and basic bots (node graph, dispatcher, Leaders). Needs: Simulation core. Exit check: headless bot-versus-bot Spawn Control matches complete, and economy rates match the throughput analysis of `reference/05_population_flow.md` within tolerance.
     - Client presentation. Contents: the renderer (terrain, instanced units and sprites, meshes, the additive and darkening pipeline states, fog, HUD), interpolation from snapshots, the camera, input bindings and the command builder, a minimal HUD with the Power slots panel, the audio engine with its event binding model and placeholder sounds, and GPU particles. Needs: Simulation core (snapshots and events) and Headless core gameplay (content). Exit check: a local Spawn Control match plays at 60 fps with 2,000 units on minimum-spec hardware.
     - Networking. Contents: the transport abstraction and its first implementation, the command sequencer (remote and in-process), a reliable command channel, jitter buffering and input delay, lobby state and validation, content-hash and version gating, divergence detection and resynchronisation, snapshot join and reconnect. Needs: Simulation core, Headless core gameplay (serialisable state) and Client presentation (the client loop). Exit check: 4 clients over a lossy link (10 % packet loss, 150 ms round trip) play for 30 minutes without divergence, forged commands are rejected, and a rejoin at minute 20 works.
     - Content breadth. Contents: the 31 crate outcomes, Power slots and the Comeback Bonus; the turrets, Beam Dishes, Solar Arrays, Barrier Emitters and Transit Gates; the creatures; Strike team, Transport, Collector, Builder, airstrike and Missile Barrage; the other five modes and their objects; bots per mode and difficulty; tutorials as step graphs. Needs: Headless core gameplay and Client presentation; Tools supply the test maps. Exit check: every mode is playable against bots on test maps, and the per-mode validators pass.
     - Tools. Contents: the map editor with in-editor play-test and per-mode validation, the terrain generator and heightfield baker, the content build with manifests, hashes and validators, a replay viewer, debug overlays (network statistics, bots, grids), sequenced cheat commands and the soak-test harness. Needs: Simulation core (headless runner) and Client presentation (renderer). Exit check: designers author and play-test a new map end to end, and the nightly soak runs every mode × map.
     - Front end and platform. Contents: the UI framework, the front-end pages (main, game select, map select, lobby, options, help, results), the localisation pipeline, platform services (entitlements, achievements, lobbies, leaderboards), crash reporting, the installer and depots. Needs: Client presentation (UI renderer) and Networking (lobby). Exit check: the complete flow from launch to results and back works, and the platform certification checklist passes.
     - Production. Contents: final art, audio and music to the role lists, balance passes from the reference baseline, performance work, accessibility and localisation. Needs: Content breadth, Tools, and Front end and platform. Exit check: content complete, balance targets met, performance budgets met.
  7. Workstreams with their first milestone and key risks:
     - simulation and determinism: the cross-machine replay-hash match; risks: the numeric model, and the discipline of simulation isolation and no statics;
     - gameplay rules and bots: headless bot-versus-bot Spawn Control; risks: rule defects re-introduced, and the breadth of per-mode bot strategies;
     - rendering and VFX: 2,000 instanced units at 60 fps; risks: keeping the reference look while using current techniques, and GPU particle caps;
     - input, camera and UI: the Power slots panel, the selection circle and Leader orders; risks: the priority order of the context resolver, and gamepad navigation;
     - audio: the event-binding engine with placeholder sounds; risks: completeness of the event list, and a new music direction;
     - networking and platform: 4 clients over a lossy link for 30 minutes without divergence; risks: platform lock-in and relay operations;
     - tools and content pipeline: a content build with hashes, and the first editor-made map; risks: editor scope and validators;
     - QA and performance, from the simulation core onward: the nightly soak and a replay corpus; risk: no reference performance figures exist.
  8. Some reference exit checks assume that every peer runs the same simulation (cross-machine hash identity as the networking prerequisite, divergence detection and resynchronisation). Their Species form depends on `decisions/deferred/networking.md`; with a server-authoritative model the cross-machine hash check becomes a reproducibility check of the server build, and the lossy-link figures (10 % loss, 150 ms round trip, 30 minutes, rejoin at minute 20) remain usable as networking targets.
  9. Species work that has no reference package and that the plan must place: region partitioning and interest-managed replication from day one (vision O1, §5); world persistence in a database, with schema migration across patches (vision O1, §6 item 7); the abstract economy model and its calibration against the full simulation (vision O3); the deputy AI under fog of war (vision §1, §5); protection rules for settlements whose owner is AFK (vision O2); the settlement status and order server API (vision O6); the headless dedicated server and its community-hosting package (vision O5); the strategic zoom level (vision O9); and the stat and modifier system with unit-specialisation hooks (vision O11).
- Options: A — the reference order adapted to Species: foundations, then the headless server core, then a headless skirmish slice, then client presentation on the integrated server with the in-process transport, then the world systems of item 9, then content breadth, tools, front end and platform, and production. B — world first: regions, persistence and the abstract model before the skirmish slice. C — client first: presentation before the simulation core.
- Recommendation: A. The skirmish on the integrated server is the earliest point where combat can be played and balanced, and it already exercises the server path, the in-process transport and the snapshot boundary that the world needs; the world systems then build on a proven server core. The transport therefore moves earlier than the reference's networking package, because the in-process transport is part of the first playable. B delays every playable milestone behind the riskiest systems, and C contradicts item 1.
- Decide by: design phase
