# Deferred decisions: networking

> Status: Decision register, deferred to the design phase · IDs: DEC-200 to DEC-208 · Related: [vision brief](../../../vision/species-vision-brief.md) (O1, O4, O5, O6, O8, O10, §5, §6), `decisions/deferred/process_tick_and_roadmap.md` (process roles, state ownership, pacing, tick rate, budgets), `decisions/deferred/numerics_lobby_terrain_services.md` (numeric model, lobby, sessions and services, persistence), `reference/12_simulation_model/`

## Scope

This file records the networking decisions that the Species design phase takes. The reference library specifies no networking model. The reference networking material is not part of the library, because Species runs a server-authoritative world: the server owns the world, clients send commands and receive only the state they are allowed to see, and one server codebase runs integrated in the client first and on dedicated servers later (vision O10 and §5). What the design phase needs from that material is kept here: the failure modes that any Species networking model must prevent, stated in Species terms, and the figures that size the design (message sizes, command rates, population and body counts, buffering and latency, timeouts).

Every entry has the status **Open** and is decided in the design phase. Its specified behaviour is what this library states today. Two extra fields support the design work. **Reference behaviour** describes, in one paragraph, the roles and properties of the reference networking model. **Constraints and lessons** lists, as numbered items, the failure modes the chosen model must prevent and the figures, with their units. Whichever model the design phase chooses, it **must prevent every failure mode listed under Constraints and lessons in DEC-200 to DEC-208**.

Not decided here, because the reference library keeps them as reference behaviour in `reference/12_simulation_model/`: the player command catalogue, the simulation random streams and their draw discipline, the per-tick update order, and the simulation-integrity rules. Decided in neighbouring files: process roles and the headless build, the simulation and presentation boundary, state ownership and reset, pacing, the tick rate and the per-tick CPU budget (`process_tick_and_roadmap.md`); the numeric model, the lobby and match-setup authority, identity, entitlement and discovery, and persistence (`numerics_lobby_terrain_services.md`).

## Model and budget

### DEC-200 Replication and authority model
- Status: Open
- Affects: the whole simulation model, in particular the player command catalogue and the integrity rules (`reference/12_simulation_model/06_teams_and_player_commands.md`, `reference/12_simulation_model/07_randomness_and_integrity.md`, R-SIM); bot execution (`reference/07_bots/`, R-BOT); the skirmish match rules (`reference/01_skirmish_rules_and_modes/README.md`, R-MODE); `architecture/components/platform_layer.md` (PLT); `architecture/components/diagnostics_test_and_performance/` (DBG-160, DBG-164: the soak runs in one process with no client until the networking model exists)
- Specified behaviour: This library specifies no networking model. The reference simulation is a deterministic, command-driven step: all player intent enters as commands from the command catalogue, and bots run inside the simulation step and issue no network traffic of their own. The vision fixes the frame of this decision: the server is authoritative and clients receive only the state they are allowed to see (vision §5); one server codebase runs integrated in the client and later as a dedicated server, behind the same transport interface (O10); replication is interest-managed and the world is partitioned into regions from day one (O1); the skirmish mode runs on the same netcode as the world (O8).
- Options: A — one server-authoritative state-replication model for the world and for skirmish: interest management, quantised delta updates, client-side interpolation; B — option A for the world, and deterministic lockstep with a server-side command sequencer for skirmish only (this departs from O8 and needs an owner decision); C — option A, plus deterministic client-side simulation of selected content (for example a battle the client is watching), re-anchored by server snapshots.
- Recommendation: A. It is the only option that meets O1, O8 and O10 with one netcode. It keeps fog of war enforceable, because a client never holds state it may not see, and it turns join and reconnect into a snapshot instead of a re-simulation. Its cost is bandwidth at crowd scale, which DEC-201 bounds. B keeps skirmish bandwidth independent of the unit count, but it doubles the netcode, puts the full determinism burden on the shared simulation and needs O8 changed; consider it only if the DEC-201 prototype shows that skirmish-size battles cannot be replicated within budget. C is a later optimisation, not a starting model.
- Decide by: design phase
- Reference behaviour: The reference uses deterministic lockstep over a server-sequenced command stream. The host's process runs a sequencer that never simulates, and every participant, the host included, runs the full simulation. Every 0.1 s the sequencer packs all commands received since its previous tick into one numbered command frame, appends it to an unbounded history and sends it to every client; each client executes the frames strictly in number order, one frame being one simulation tick spread over 10 update slices. Besides commands, only a one-byte divergence value per frame flows back to the host. There is no dedicated server; solo play uses the same pipeline in-process, and the lobby state travels in the same sequenced stream. Lockstep is the reference model. Species does not use it for the world (O10); the design phase may consider it for skirmish only (option B).
- Constraints and lessons:
  1. Crowd scale: a reference match has 6 team slots (up to 4 players, human or Bot, plus the Rogue faction and the Visitor faction, both always present as bot teams) and about 2000–6000 simulated objects at peak. DEC-201 has the figures.
  2. The bandwidth advantage of the reference model (commands only, independent of the unit count) exists only while every process runs a bit-identical simulation; any determinism defect becomes a divergence. The reference holds its four preconditions (one total order of inputs, identical initial state, bit-identical arithmetic, strict separation of simulation and presentation randomness) by discipline, not by construction.
  3. The server is the only writer of simulation state. Client code that writes a simulated field is a defect: in the reference, UI code resets a replicated Power field on the owning client only, render code assigns a new type to the selected building on the local client, and simulation objects hold wall-clock timers that the simulation step edits.
  4. In the integrated stage the server runs in the host's process. The simulation must read no host-local state: one of the reference's live divergence paths comes from Strike team direct control, which runs in the simulation for every team and reads the local camera's free-look flag. The integrated server reaches host input only through the transport interface, never through process-global state (camera, preferences, wall clock, UI singletons). `process_tick_and_roadmap.md` DEC-222 decides the boundary itself.
  5. Client-side previews must not consume simulation resources: the reference allocates its per-frame route-preview lines from the same pool as simulation routes, so the route ids handed to Workers can differ between processes. In the integrated stage, client previews never allocate ids from the server's pools.
  6. Every state change a player can cause travels as a command. A client-local shortcut that changes simulation state is a defect; the reference has dormant ones (a local cancellation of a Power, a local toggle of a world object) that would diverge if reached.
  7. State that survives between matches or battle instances in one process makes results depend on the process's history: in the reference, the Control Zone count that Flag Chain's airstrike threshold reads is reset only when a Zone Control match starts, so processes with different session histories diverge. A server that runs many battles, regions or skirmish matches in one process owns all mutable simulation state per instance (`process_tick_and_roadmap.md` DEC-223).
  8. Bots in the reference run wherever the simulation runs, issue no network commands and read the full simulation state; their CPU cost (for example quadratic target scans and per-cycle loops over all building pairs) is paid by every process that simulates. In Species they run on the server, and under vision §5 the inputs of settlement AI and the deputy are filtered to what their settlement may see, by the same interest rules as replication.
  9. The server builds and runs headless (vision §5, `process_tick_and_roadmap.md` DEC-220); the same headless simulation serves soak tests, replay validation and dedicated hosting.
  10. If option B is chosen for skirmish, the lockstep preconditions become mandatory there: fixed integer ticks, per-match state, the reference random-draw discipline, per-tick hashing of canonical state (DEC-206), command authority at the sequencer (DEC-202), content and version identity (DEC-204), snapshot-based join (DEC-205), a pinned numeric model (DEC-240), bounded searches with deterministic fallbacks, and replays that store the seed. A sequencer that never simulates is cheap to host; an optional headless referee simulation per match can attribute divergences and validate results.

### DEC-201 Replication bandwidth and population budget
- Status: Open
- Affects: population caps and Essence orbs (`reference/05_population_flow.md`, R-ECON); the simulated-object kinds (`reference/12_simulation_model/03_entity_model_and_identity.md`, R-SIM); performance budgets (`architecture/components/diagnostics_test_and_performance/`, DBG); vision §6 items 4, 5, 6 and 12
- Specified behaviour: This library states the reference population caps and the kinds of simulated objects. It states no network budget. Battle-size and world-population limits are open (vision §6 item 4); the per-tick CPU budget and the stress populations are decided in `process_tick_and_roadmap.md` DEC-228.
- Options: A — budget first: fix a downstream and an upstream budget per client and explicit battle-size limits, then design the replication encoding to fit; B — capacity first: design for the reference population caps and measure the bandwidth that results; C — aggregated crowds: replicate crowds as group state (formation, density, seeds for per-figure variation), with full per-figure state only near the viewer.
- Recommendation: A, with C as the main technique to evaluate. Set a per-client downstream budget (a target in the tens of KB/s at 16 players) and an upstream budget, derive the visible-figure limit from them, and prototype a 2000-figure battle before the world's population caps are fixed. The figures below show that per-figure replication of a full reference battle needs hundreds of KB/s per client raw; only interest management plus aggregation brings it near such a budget.
- Decide by: design phase
- Reference behaviour: The reference replicates no world state: every process simulates the whole world and receives only commands, so its bandwidth does not depend on how many bodies are alive. The downstream stream per client is one command frame per 0.1 s that holds every team's commands and continuous control state, plus repair copies of earlier frames; with four players and no other commands one frame is about 240 bytes. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Population per reference arena: a cap of 1400–2000 bodies per map. Of the 49 standard arenas, 1 has 1400, 9 have 1500, 2 have 1600, 15 have 1800 and 20 have 2000; the 2 cooperative arenas are uncapped.
  2. Population per team: the map cap divided by the number of players, 350–1000 bodies, counted over the team's free bodies (Workers, Leaders, Transport units, Builders, Collectors and a bot team's bot controller), excluding Crawlers. Reinforcements, supply crates and Collectors can take a team over its cap.
  3. Essence orbs: one per death (none for the Rogue faction); each stays collectable for 30–50 s and then ascends for 90 s, so thousands exist after a large battle.
  4. Laser bolts: every Worker shot is a simulated object. With a 3 s reload, 2000 Workers in combat create up to about 670 laser bolts per second.
  5. Searches: every Worker runs a full search for something to do every 1–2 s, staggered, so 2000 Workers make about 1000–2000 full searches per second (server CPU, not bandwidth).
  6. Simulated objects at peak: about 2000–6000 (units, Essence orbs, laser bolts, effects and buildings).
  7. Estimated cost of per-object state replication at that scale: hundreds of KB/s per client raw; tens of KB/s with quantisation, delta compression and interest management. In the reference interest culling buys little, because there is no fog of war; Species has fog of war (vision §5), which is what makes interest management effective.
  8. Command-only traffic for comparison: about 5 KB/s per client downstream and about 1 KB/s upstream in a quiet 4-player match, independent of the unit count. Sending continuous control state at 20 Hz instead of 10 Hz doubles it, and at 30 Hz triples it.
  9. Command traffic is small and independent of the population: one team's continuous control state is a few tens of bytes, and a 4-player command frame that holds only control state is about 240 bytes, or about 480 with a repair copy (item 8). Commands alone never grow with the number of bodies; state replication does.
  10. Precision: moving bodies carry position, velocity and facing, and positions are the largest part of their state. A quantised encoding relative to a region origin is the main lever on bandwidth, and it also addresses coordinate precision far from the world origin (vision §6 item 6).
  11. Per-field overhead: a self-describing message format that names every field costs several bytes per field, which state replication at crowd scale cannot afford. A schema-defined binary layout without per-field names is needed for state replication (DEC-207).
  12. The reference has no bandwidth limiting or adaptation, only measurement. Species needs a sender-side budget per client with graceful degradation (lower update rates for distant or aggregated crowds) instead of queue growth.
  13. No measured simulation cost at the population cap exists for the reference; the server CPU per battle, and so the number of concurrent battles a server can run, must be measured on a prototype (`process_tick_and_roadmap.md` DEC-228 holds the per-tick budget figures and the stress populations).

## Commands and input

### DEC-202 Command validation and authority
- Status: Open
- Affects: the player command catalogue (`reference/12_simulation_model/06_teams_and_player_commands.md`, R-SIM; R-SIM-452: the commands that no input issues, `ReportScores` among them); controls and commands (`reference/06_controls_camera_and_commands/`, R-CTRL); lobby and match setup (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`, R-META); developer cheats (`architecture/components/diagnostics_test_and_performance/`, DBG); vision O6
- Specified behaviour: This library specifies the command catalogue and the rules each command applies when it executes. It specifies no check on who sends a command. The vision requires settlement status and deputy orders to be a server API (O6). Who may change lobby and match-setup state is decided in DEC-243.
- Options: A — the server validates every command when it arrives: the sender's identity and its ownership of the addressed team or settlement (or its right to host-only and operator-only commands), the phase (lobby, match, world, battle), argument ranges and the validity of every id; a rejected command is dropped, logged and counted; B — option A, plus revalidation when the command executes, against the state at that tick, with a defined no-op when the target has changed; C — trust the client for low-risk commands (camera, selection) and validate the rest.
- Recommendation: B. Validation on arrival stops forgery. Revalidation on execution is needed because the state changes between issue and execution (the input delay of DEC-203), and the reference shows that a move order whose group emptied in the meantime produces an undefined route. One validation path serves the game client, the deputy, settlement AI and the O6 server interface, so no route into the simulation bypasses it.
- Decide by: design phase
- Reference behaviour: The host's sequencer accepts any command from any registered client, adds the sender's address and forwards it in the next command frame, and every process executes it. A command's validity is decided only by its handler when it executes, identically on every process, so a forged command is not a divergence but a successful cheat. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Ownership: the reference forwards any team command from any registered client and checks only that some team is named. A modified client can order, select, cancel a Power, promote or demote a Leader for another team, toggle another player's ready state, change the match options or start the match. Lobby restrictions exist only in the UI.
  2. Phase: no command is checked against the phase, so match commands are accepted in the lobby and lobby commands in a match.
  3. Missing fields: a typed read of a missing or mistyped field returns a fixed default that looks like a valid value (for the team field, a valid-looking team number instead of the "no team" marker), so a message that omits the team field passes the reference's only check. A missing or mistyped field rejects the command.
  4. Id width and sentinels: the ids of running Powers travel in one byte, so ids of 256 and above alias, and one value is reserved in-band as a sentinel and cannot itself be cancelled. Commands carry stable generational ids of at least 16 bits, never pool slot indices and never in-band sentinels.
  5. Commands issued by the simulation: executing one Leader toggle command on every process makes each process issue a further selection command, so one click becomes N identical commands (harmless only because the sequencer keeps one selection per client per tick). The simulation never issues player commands as a side effect (DEC-119). A bot or deputy order is a command from an authorised source and passes the same validation.
  6. Duplicates: one click with nothing selected issues two identical selection commands. Commands are idempotent or deduplicated per client per tick.
  7. Execution-time state: a move order for a group whose members all died between the click and its execution divides by the group size of zero and starts its route at an undefined position. Every command handler defines its result when its target no longer exists; a crowd order for an empty group does nothing (DEC-555).
  8. Developer cheats (arbitrary placement, resource changes) are unvalidated local actions in the reference, and some of them diverge. In Species a cheat is a command that only an authorised operator may send, validated by the server. Reference cheats that change simulation state: kill all enemies; spawn Workers for each of the six team slots; spawn a Transport, Crawlers or Essence orbs (the last draws 20 values from the simulation generator); spawn structure ports; spawn a Supply crate; and allow arbitrary placement, which changes only the local placement check that every participant repeats when the placement command executes, so in Species it is a session rule that the server applies, not a client flag. Cheats with no simulation effect: the profiler, sound editor, sound statistics and network statistics windows, and a render-resource reset, after which trees regenerate from the same per-tree seed. Until this entry is decided, the host's own participant is the only authorised sender of debug commands in a session created with cheats enabled, and the authority drops, logs and counts a debug command from any other sender (`architecture/components/diagnostics_test_and_performance/` DBG-118).
  9. Vision O6: the authenticated interface for settlement status and deputy orders reaches the simulation through the same validation as in-game commands.
  10. Rate: a reference client sends its continuous control state every 0.1 s plus its discrete commands. One command frame crosses the reference's datagram limit at about 30 option-change commands or about 25 control-sized commands in one 0.1 s tick (DEC-207). The server needs a per-client command-rate limit, so a flood is dropped and reported instead of queued.

### DEC-203 Input timing, coalescing and latency
- Status: Open
- Affects: tick timing, update slices and render interpolation (`reference/12_simulation_model/01_tick_timing_and_main_loop.md`, R-SIM); the continuous control state and the one-shot actions (`reference/06_controls_camera_and_commands/`, R-CTRL); `architecture/components/input/` (INP)
- Specified behaviour: This library specifies the reference tick (10 per second, each executed as 10 update slices) and the team command state (`TeamCommandState`) that holds each team's continuous control state. It specifies no input delay, jitter buffer or coalescing rule. The tick rate is decided in `process_tick_and_roadmap.md` DEC-227 and the loop pacing in DEC-225.
- Options: A — a fixed input delay with a jitter buffer on the server (each command is stamped with the tick it executes in), and a fixed interpolation delay for received state on the client; B — option A, plus client-side prediction of local feedback only (cursor, selection highlight, order markers, camera), never of unit movement; C — an adaptive delay that follows the measured jitter.
- Recommendation: B. Crowd commands tolerate 100–200 ms of delay (a lockstep design at 20 Hz with 2 ticks of input delay gives 100 ms plus half the round trip), so unit movement needs no prediction, and immediate local feedback hides the delay. Fix the delay values on the prototype; make them adaptive (C) only if measurements demand it. Adopt the coalescing rule of constraint 1 whatever the model.
- Decide by: design phase
- Reference behaviour: Each client sends its continuous control state every 0.1 s together with its discrete commands. On its 0.1 s tick the sequencer packs the discrete commands in arrival order, then each client's latest control state and latest selection, and every process applies them at the start of that command frame. The client spreads each frame's 10 update slices across its render frames by a backlog rule. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Coalescing: the reference keeps only the latest continuous control message per client per tick and discards earlier ones whole, so the one-shot actions inside an earlier message (a click, fire, a move target) are lost, and a tick in which no message arrives applies no input for that team (no fire, no direct control; the cursor position is kept). This is lost or late input on every process alike, not a divergence. Coalesce only continuous state (cursor position, stick vectors, selection: latest wins, held when a tick receives none); deliver one-shot actions exactly once, in order, as discrete commands.
  2. Latency composition in the reference: the wait for the next sequencer tick (uniform 0–100 ms), plus the round trip, plus the client's pacing delay. The host has no network latency but the same tick quantisation and buffering.
  3. Latency tied to the render rate: the reference client executes ⌊0.3 · P⌋ of its P pending update slices per render frame. The mean backlog at the start of a render frame is about 7.0 slices at 60 fps, 12.7 at 30 fps, 17.0 at 20 fps and 23.3 at 15 fps; the delay from a frame's arrival to its last slice is 100 ms at 60–120 fps, 133 ms at 30 fps, 150 ms at 20 fps and 217 ms at 15 fps, plus up to one render frame for frames that arrive between render frames. A backlog of 3 slices or fewer is never drained before the next frame arrives. Command latency must not depend on the client's render rate: use an explicit, fixed delay buffer.
  4. Sequencer bound to a frame rate: the integrated reference sequencer advances at most one tick per host render frame, so the tick rate depends on the host's frame rate and vsync, and a host below 10 fps slows the whole session. The Species integrated server ticks on its own clock, independent of the host client's frame rate (`process_tick_and_roadmap.md` DEC-225).
  5. Catch-up: a lagging reference client is sent 3 command frames per tick (30 per second), so it gains 20 frames per second on the production of 10 per second.
  6. Lockstep figures for comparison, a lower bound for perceived command latency: an input delay of 2 ticks gives 100 ms plus half the round trip at 20 Hz, 67 ms at 30 Hz and 200 ms at 10 Hz.
  7. Display: presentation runs at display rate and interpolates between the last two simulation states, with a fixed one-tick display delay. A replicated client interpolates between the last two received states, so its interpolation delay adds to the command delay and belongs in the latency budget.
  8. Pause and game-speed changes are commands that take effect at a stated tick on the server; game speed changes the number of ticks per second, never the length of a tick. The pause rules themselves are reference behaviour (`reference/12_simulation_model/`).

## Identity and sessions

### DEC-204 Content and version identity
- Status: Open
- Affects: map identity (`reference/08_maps_and_level_design/rules_and_conventions.md`, R-MAP); custom maps (`reference/08_maps_and_level_design/map_editor_hooks.md`, R-MAP); the pack file and the content build (`architecture/components/asset_pipeline_and_resources.md`, AST); the build identity (`architecture/components/build_tooling_and_distribution.md`, BLD); `architecture/components/data_schemas/` (DAT)
- Specified behaviour: This library identifies maps by a checksum of their content, for menus and lists. It specifies no exchange of content or version identity between processes. Persistence and world-save migration across patches are decided in DEC-250 and DEC-251.
- Options: A — the content build emits a manifest with a hash of every simulation-relevant asset and one combined content hash; every build carries a generated identity (release version, repository revision, simulation version, protocol version); the server refuses a client whose protocol version or content hash differs, with a clear reason; B — option A, plus download of custom or community content (maps now, mods later) from the server after the hash check; C — server-only simulation content: clients load presentation assets only and receive simulation data from the server.
- Recommendation: A at launch, designed so that B can follow, because community servers (O5) and later modding (vision §7) will need it. Under server authority the server is the only process whose simulation data must be right, but clients still need matching content for presentation, interpolation and any local feedback, and a mismatch must be refused with a reason, never played.
- Decide by: design phase
- Reference behaviour: The reference computes a 32-bit checksum of each map file at run time. It uses it to place the map in the per-mode menus, to filter server listings for maps a player does not have, and to gate which maps may be played. A match itself is chosen by file name, and nothing about content or version is compared between processes before the simulation starts. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. A match is started by map file name, and no content identity is compared between processes, so a locally edited map diverges instead of being refused.
  2. Simulation data files (unit stats, rules, collision shapes, match option tables, terrain seeds) are never hashed or compared.
  3. The build version string is the same for every build and is compared only in the client's server browser; the host accepts any joiner and records no version, so builds that compute differently, such as a Debug and a Release build, can play together and diverge. Every peer of a session runs the same build identity (ADR-057), and version gating belongs on the server.
  4. Debug builds whose instrumented random draws compute differently from release builds never play with release builds; the build identity says which kind a build is.
  5. The identity is a checksum of the file bytes, so any edit (including a whitespace change, or a load-and-save round trip in the map editor) changes the id and silently breaks every list keyed by it: the map menus, the permitted-map lists and the tutorial's fixed maps. Content is identified by a hash of its canonical form, produced by the content build, and lists are keyed by a stable content name together with that hash.
  6. The identity is computed over whichever copy of a file wins at load (a loose file or the archive entry), so a loose file silently changes it. With no loose-file override in a shipping build (the pack-file rule of the engine ADRs), the manifest is authoritative.
  7. Simulation-relevant data derived at load time must be content or a deterministic function of content: the reference generates tree collision spheres at load from a shared presentation generator that is neither synchronised nor thread-safe, so the collision data can differ between processes.
  8. Sizes: Species custom maps and world-region data can be far larger than a skirmish map, so hashing and transfer (DEC-207) stream the data instead of buffering it whole, and no reader assumes a bound on a map file's size that it does not check.

### DEC-205 Join, reconnect, leave and session continuity
- Status: Open
- Affects: players leaving and the Bot takeover (`reference/01_skirmish_rules_and_modes/README.md`, R-MODE); match flow and loading (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`, R-META-056, R-META-059, R-META-092); spectators; vision O2, O4 and O10
- Specified behaviour: This library keeps the reference rule that a player who leaves a match is replaced by a Bot at once. A joining participant that has received a message from the host and then receives none for `ref.meta.connect.host_silence_limit` (5.0 s of real time) ends its session and shows `ui.error.connection` with the title page as its back page, on any page and in a match; while it is still connecting it waits without a timeout (R-META-056, R-META-059, R-META-092). The library specifies no late join, reconnect, slot reclaim, spectating or host-loss behaviour. The vision makes AFK play normal (the deputy acts, O2) and freezes the world while its server is not running (O4).
- Options: A — snapshot plus delta join for every case (first join, late join, reconnect, spectator, moving between regions), with a session token that lets a returning player reclaim their team or settlement from its Bot or deputy stand-in; B — option A, plus migration of the integrated server to another player's process when the host leaves; C — option A, and in the integrated stage the session ends cleanly for remote players when the host leaves (the world freezes, O4); continuity comes from dedicated servers.
- Recommendation: C. O4 makes the loss of the host a freeze by design, so host migration (B) buys little for its cost, and O10 moves the world to dedicated servers. Snapshot join makes the time to join independent of how long the world or match has run.
- Decide by: design phase
- Reference behaviour: A joining client retries until the host assigns it an identity, then receives every sequenced command frame from the first one, lobby included, and re-simulates them all before it counts as caught up. A player who leaves a match becomes a Bot on every process at the same frame, because the leave notice is itself a sequenced frame; in the lobby the slot is freed instead. The session lives in the host's process and ends with it. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Join by replay does not scale: a reference late joiner re-simulates the whole session at a catch-up rate of +20 frames per second, so joining a 20-minute match takes about 10 minutes, and the command history is never trimmed. A persistent world rules replay-based join out; join is a snapshot. A suitable acceptance target: a rejoin at minute 20 completes in under 10 s.
  2. A returning reference player gets a new identity while the Bot keeps their team; nothing reclaims the slot. The departed player's reserved slot can count toward the player limit and so block a rejoin into a full match.
  3. When the host quits, the integrated reference server is destroyed and the session ends for everyone; the remote clients see only a lost-connection notice.
  4. In the lobby a leaver's slots are freed; in a match they stay reserved and pass to a Bot. In the Species world a player leaving is the normal AFK case: the deputy takes over (vision §1, O2), and the session token restores direct control.
  5. Timeouts in the reference: the server drops a client after 20.0 s without any message; a client shows a lost-connection notice after 5.0 s without a server message, and the end-of-match flow treats a client silent for more than 5 s as lagged; the network statistics view marks a client lost after 2.0 s; a connecting client retries every 1.0 s with no attempt limit; a team request or colour request is repeated every 0.1 s and a team name every 1.0 s until echoed; a graceful leave sends its leave message 3 times and then waits 100 ms.
  6. Loading: while a client loads a level it keeps the session alive with a message every 1.0 s. Keep the keep-alive and add progress reporting.
  7. Connection states the reference distinguishes: disconnected; connecting (retrying); handshaking (identity assigned, catching up, no team yet); connected (team requests allowed). The identity reply bypasses the sequenced stream and is placed ahead of it.
  8. Disconnect reasons the reference reports to the leaving player: left voluntarily; dropped after the timeout; server full; invalid entitlement; duplicate identity; wrong password; kicked by the host. Each needs player-facing text, and "server full" and "wrong password" return the player to the join screen.
  9. A removed client that keeps sending is answered with a repeated disconnect notice, and the records of disconnected clients are kept for the server's whole lifetime. A dedicated server that runs for weeks needs bounded records.
  10. Spectating exists in the reference only in a test configuration. It is cheap with a snapshot plus the update stream, and it needs an optional delay so that it does not leak live information.

## Integrity, transport and diagnostics

### DEC-206 Divergence detection and integrity checking
- Status: Open
- Affects: the simulation-integrity rules and random streams (`reference/12_simulation_model/07_randomness_and_integrity.md`, R-SIM); the match lifecycle (`reference/12_simulation_model/02_match_lifecycle_and_state_reset.md`, R-SIM); divergence dumps and soak tests (`architecture/components/diagnostics_test_and_performance/`, DBG); the replay hooks
- Specified behaviour: This library keeps the reference random-draw discipline, the per-tick update order and the simulation-integrity rules. It specifies no run-time divergence check.
- Options: A — a 64-bit hash of a canonical serialisation of all simulation state, computed every tick (or maintained incrementally) in every build wherever two simulations of the same inputs must agree, with a structured field-level diff at the first failing tick; B — the same hash in test and CI builds only; C — no run-time hashing; rely on server authority and on CI replays.
- Recommendation: A. Under server authority no two processes simulate the same world live, but Species still runs the same inputs twice in several places: CI and soak replays, the headless server compared with a full client, a region's state handed between server processes (O1, where the hash proves the transfer), replays, and the lockstep skirmish if DEC-200 option B is chosen. A per-tick canonical hash in every build is cheap and pins every determinism defect to the tick it happens in.
- Decide by: design phase
- Reference behaviour: After each command frame every process sends a one-byte value to the host. When the values of all processes for a frame have arrived and differ, the host flags every process whose value no other process shares and announces the flag in the sequenced stream, so every process freezes at the same frame. Debug builds also exchange full state snapshots through a reliable blob transfer and mark the differing objects in the world. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Weak detection: the reference's per-frame value is one byte taken from the next simulation random draw, so it detects only a different count of random draws, not different state; a state divergence is noticed only once it changes a branch that draws. When draw counts differ, the bytes still collide with a probability of 1/255 per frame (the chance of escaping detection for k frames is 255^−k: about 0.4 % for one frame and 1.5 × 10^−5 for two).
  2. Partial coverage: the debug-build snapshot hash covers the positions, velocities and facings of units, bodies, laser bolts, effects and buildings, slot validity, the network time and one random sample. It omits health and stats, body and building states and timers, building ownership, Essence orbs, Power slots, bot state, scores and mode state, game speed, the actor grid cache and routes. A useful hash covers all simulation state through one canonical serialisation.
  3. Debug only: the full snapshot exists only in debug and test builds; release builds carry the one-byte value. The check runs in every build.
  4. Terminal reaction: a detected divergence freezes the simulation for every process at the same frame, permanently, with no resynchronisation; play resumes only when the flagged client leaves. With 2 processes both are flagged, so nobody can be blamed. The reaction to a detected divergence is a resynchronisation from the authoritative state, or a graceful end that preserves the result.
  5. Wrong attribution: the divergence notice names the client by its array position and the leave notice by its client id; after any earlier leave the two differ, so the wrong client can be blamed or cleared. Clients are named by stable ids everywhere.
  6. Forensics: on divergence each process writes a world-state dump at the failing frame, one line per body, effect and building, with vector quantities summarised as the sum of their components, which hides some differences. Keep the dump as a structured, field-level diff of both states at the failing tick.
  7. Instrumentation must not change arithmetic: the reference's draw-tracking debug build computes its symmetric random fraction by a different formula from the release build, so tracked and untracked processes diverge. Its call log keeps the last 100 000 draws, each with its call site and a running counter, which is the right tool for finding the first divergent draw.
  8. Cost: the reference formats a state line before and after every body and building update even in release builds, where the log is discarded. Diagnostic logging costs nothing when disabled.
  9. Replays from the command stream need the seed, the build identity, the content hashes and the team layout. The reference's command-history recording stores no seed and is loaded after the replaying session has started its own match, so it cannot reproduce a match.
  10. Areas of the reference simulation most prone to divergence: terrain heights and trees, Barrier Emitters, Relics, the dust vortex, and Leaders directing Workers into Beam Dishes. A determinism test corpus starts with them.
  11. The abstract economy model (O3) is not expected to reproduce the full simulation exactly; its accuracy is a calibration measure, not an integrity check.

### DEC-207 Transport, message format and robustness
- Status: Open
- Affects: sockets, threads and the transport interface (`architecture/components/platform_layer.md`, PLT); the typed message container, which also stores custom maps (`architecture/components/data_schemas/`, DAT); custom-map files (`reference/08_maps_and_level_design/map_editor_hooks.md`, R-MAP)
- Specified behaviour: This library specifies no transport and no network message format. Identity, entitlement, encryption keys and discovery are decided in DEC-248 and DEC-249.
- Options: A — a platform transport with relay servers, NAT traversal and encryption, behind a Species transport interface; B — an own encrypted datagram transport with reliable and unreliable channels and fragmentation, behind the same interface; C — a stream transport for commands and a separate datagram channel for state.
- Recommendation: decide together with DEC-200 and the services decision; adopt the constraints below whichever transport is chosen. B suits community-hosted dedicated servers (O5) best, because it depends on no platform service; A eases the integrated stage, where players host from home networks. Either way the integrated server (in-process, no sockets) and the dedicated server share one interface (O10).
- Decide by: design phase
- Reference behaviour: The reference sends unreliable datagrams in a star around the host, with its own resend: server-to-client command frames are made reliable by numbered resends with cumulative acknowledgements, and client-to-server messages are repeated by the application. Its messages are self-describing, with a name on every field. There is no encryption, no fragmentation and no bandwidth limiting. The Species transport is this decision, behind the one transport interface of DEC-200 (O10). Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. Reliability: client-to-server messages in the reference are fire-and-forget. Reliability comes from application-level repetition: control state every 0.1 s, a join request every 1.0 s, team and colour requests every 0.1 s and the team name every 1.0 s until echoed, a per-frame divergence value, and a leave message sent 3 times. Species needs a reliable ordered channel with acknowledgements for commands, and an unreliable latest-wins channel for continuous state.
  2. Datagram size: the reference receives into a 1500-byte buffer and writes any size in one send. A command frame larger than that is never delivered: it is resent forever, the client cannot pass that frame, shows a lost-connection notice after 5 s and never recovers. A frame crosses the limit at about 30 option-change commands or about 25 control-sized commands in one 0.1 s tick. Enforce a payload budget of about 1200 bytes per datagram, fragment above it, and assert the budget at the sender.
  3. Repair: each tick the reference server sends each client up to 3 command frames, and resends the oldest unacknowledged frame whenever the round trip exceeds one tick. A client more than 10 frames behind is caught up from its last acknowledged frame until it is fewer than 6 frames behind, and runs of empty frames are sent as one message. Acknowledgements are cumulative. Repair traffic adds to the frame size, so it counts against the datagram budget of item 2.
  4. Parsing: the reference's message container bounds some counts and lengths but not child counts, nesting depth or blob lengths; an oversize array is fatal; and an out-of-range string length misparses the rest of the message. Malformed nested packets can exhaust memory or stack. Use a bounded, versioned, schema-checked, length-prefixed format with hard limits on every count, length and depth, and fuzz the parser in CI.
  5. Unknown messages: one unrecognised command in the reference's discovery traffic aborts the process, so a single crafted datagram sent to a listening socket crashes the game. Unknown or malformed messages are dropped and counted, never fatal.
  6. Missing fields read as plausible defaults instead of errors (DEC-202 constraint 3).
  7. Short field codes reused with different meanings in two message families cause filter bugs. Each message type has its own schema.
  8. Secrets: the join password travels in clear text and is compared exactly. The transport is encrypted and no credential travels in clear text.
  9. Threads and errors: in the reference all sequencing and sending happen on the main thread, and a failure to bind the server's socket is not reported. Species does network I/O on its own thread with lock-free queues to the simulation, and reports a bind failure.
  10. Reliable blob transfer (used for divergence snapshots in the reference): 1024-byte blocks; an initial window of 10 blocks that shrinks by one per timed-out block (minimum 1) and grows by one per acknowledged block; an initial round-trip estimate of 0.1 s, smoothed as 0.9 × estimate + 0.1 × sample; a block timeout of 3 × the round trip; each acknowledgement sent 3 times; at most 256 block numbers per acknowledgement. Species transfers far larger blobs (snapshots for DEC-205, custom content for DEC-204), so it needs streamed transfer with flow control.
  11. Integrated server: the host's own client hands its messages to the in-process server directly, without sockets, but through the same sequencing and acknowledgement pipeline as remote clients. Keep that property (O10): one code path, with the transport as the only difference.

### DEC-208 Network diagnostics and test tooling
- Status: Open
- Affects: the network statistics view, divergence dumps and reproduction aids (`architecture/components/diagnostics_test_and_performance/`, DBG)
- Specified behaviour: The diagnostics component keeps a network statistics view as a developer tool. Its metric set is open.
- Options: A — a developer metric set for the authoritative model: per client, the measured round trip, jitter, loss, downstream and upstream rates against budget, snapshot age, interpolation buffer depth, reliable-channel backlog and rejected commands; per server, tick-time percentiles, entities replicated per client and bandwidth per region; plus a link simulator and input-stream record and replay; B — option A, also published as live telemetry for community-server operators (O5).
- Recommendation: B. Community operators (O5) size and tune their servers with the same numbers the developers use; consent and telemetry transport follow the engine's telemetry ADR.
- Decide by: design phase
- Reference behaviour: The reference has a developer window, toggled by a key, that shows the health of its lockstep transport: frame lag, catch-up state, gaps in the client's incoming frames, divergence flags and send and receive rates. Players see no network-quality indicator other than a lost-connection notice after 5 s. Lockstep is the reference model; Species does not use it for the world (O10).
- Constraints and lessons:
  1. The reference view shows lockstep health only: the server's last frame number and its send and receive rates; per client (at most 6 rows) the address, last acknowledged frame, name and status, and a divergence flag. The status shows the client as lost after 2.0 s without a message, a catch-up percentage while it is behind, and otherwise an estimated latency of (server frame − client frame) × 100 ms. The client side shows its next 10 frame numbers as a strip of boxes (ideally 0 or 1 filled, with no gaps), the estimated server frame and the estimated latency.
  2. Latency is estimated from frame lag in 100 ms steps; a round-trip measurement exists but is never triggered. Species measures the round trip directly.
  3. Rates are 5-second averages in bytes per second, updated only when traffic is counted; the server counts 32 bytes of header per datagram, while the actual network and transport headers are 28 bytes. Species defines rates over fixed windows and states whether headers count.
  4. Number-formatting defects make every rate in the reference view unreadable. The view needs tests.
  5. Link simulator: the reference has a disabled one that adds latency, random loss and a bytes-per-second cap (its test profile is 200 ms, 25 % loss and 8000 B/s). Species needs one in every development build, with reordering added, for soak tests; a suitable soak target is 10 % packet loss with reordering.
  6. Reproduction aids worth keeping: record and replay of the input stream; a fixed time step during replay (the reference's default replay rate is 25 frames per second); a forced seed per test match, with the seed and the first divergent tick logged; deliberate packet drop on a key in debug builds.
  7. The reference view's limit of 6 client rows is hard-coded. A world server with up to 200 clients (O1) needs a sortable, filterable or aggregated view.
