# Transport: one interface with an in-process implementation and one on MsQuic, with reliable streams, QUIC datagrams and TLS 1.3, schema-defined messages, player identity keys, build and content identity, and network diagnostics

## Context and Problem Statement

The integrated server runs in-process behind the same transport interface as a dedicated one (O10); community operators host dedicated servers first (O5). The reference sends unreliable datagrams with its own resends, self-describing messages that name every field, no encryption, no fragmentation and no bandwidth limit; a frame above 1,500 bytes is never delivered, one unrecognised message ends the process, and the join password travels in clear text (DEC-207). It compares no content or build identity between processes (DEC-204), and its network view shows only the health of its command frames (DEC-208). Identity, entitlement and the rendezvous and relay services for hosts at home are area D5's (DEC-248, DEC-249). R14 allowed no third-party library in the executable until the owner added MsQuic, Microsoft's QUIC library in its Schannel build, to the allow-list at gate B (O44, [ADR-089](ADR-089-msquic-transport-package.md)). Windows ships DTLS 1.2, and no later DTLS, in its Schannel security provider from Windows 10 version 1607 and Windows Server 2016 on; TLS 1.3, which QUIC requires, from Windows 11 and Windows Server 2022 on; and a key store and elliptic-curve signatures in CNG.

Which transport and message format does Species use, how is it secured, how do a returning player and a server know each other, how do server and client prove they run the same build and content, and what does the network report?

## Decision Drivers

* One code path whether the server is in-process or remote (O10, DEC-207 item 11).
* No dependency on a platform service for community servers (O5), and no third-party library outside R14's allow-list.
* Robust parsing of hostile input, encryption and no credential in clear (DEC-207 items 4 to 8), with no cryptographic or transport protocol of Species' own.
* A lost state update never delays a command, and a lost command never delays a state update.
* A returning steward reclaims the settlement without a platform account (DEC-205).
* State replication at crowd scale cannot afford field names (DEC-201 item 11).
* A mismatch of build or content is refused with a reason, never played (DEC-204).
* Operators tune their servers with the numbers the developers use (DEC-208).

## Considered Options

* A — a platform transport with relay, NAT traversal and encryption, behind a Species interface
* B — Species' own datagram transport with reliable and unreliable channels and fragmentation, secured by the operating system's DTLS 1.2, behind the same interface (A2's proposal before gate B)
* C — a stream transport for commands and a separate datagram channel for state
* D — QUIC through MsQuic's Schannel build: one connection per client with reliable streams for commands and blobs and unreliable QUIC datagrams for state updates, secured by TLS 1.3, behind the same interface (the owner's proposal at gate B)

## Decision Outcome

Chosen option for the transport: "D", decided by the owner at gate B (O44) and recorded with its package in [ADR-089](ADR-089-msquic-transport-package.md); with option A of DEC-204 for identity and option B of DEC-208 for diagnostics. The record stays Proposed until its evidence exists. **Default while Proposed:** the decision below, which the MVP builds from its milestone M4 (MVP-071).

1. **One interface, two implementations.** `Transport` is the interface of every connection: connect, accept, send on a channel, receive, close, and its statistics. `InProcessTransport` joins the client and the integrated server by bounded queues of encoded buffers, through the same sequencing, acknowledgements, channels and interest tiers. `QuicTransport` is the remote implementation: one QUIC connection (RFC 9000) per client through MsQuic, whose streams and datagrams carry the channels of item 2; MsQuic owns the UDP socket, so neither Species code nor the platform layer opens one (ADR-089). A relay hop for hosts behind a home router (DEC-249) is a third implementation behind the same interface when a provider is chosen with the storefront (O45, O49).
2. **Channels.** The reliable, ordered channel for commands, presentation events that are guaranteed, results and replies is one bidirectional QUIC stream that the client opens when it connects. The unreliable, sequenced channel for state updates, and upstream for the client's control states (ADR-087 item 5), is QUIC DATAGRAM frames (RFC 9221), which are never retransmitted; MsQuic reports each one as acknowledged or lost (`QUIC_DATAGRAM_SEND_ACKNOWLEDGED`, `QUIC_DATAGRAM_SEND_LOST_SUSPECT`, `QUIC_DATAGRAM_SEND_LOST_DISCARDED`), and an acknowledged update becomes the client's baseline (ADR-086), so Species keeps no sequence or acknowledgement fields of its own. The streamed transfer of blobs (a join's snapshot, terrain chunks by digest, a replay) is one unidirectional stream per transfer under QUIC's flow control, never buffered whole (DEC-204 item 8, DEC-207 item 10), within the blob budget of ADR-086 item 4. A lost packet delays only the stream it carried; it never holds a datagram or another stream. Each connection names its role by its TLS application protocol (ALPN): `species-play` for a client session and `species-admin` for the administration interface of item 7.
3. **Datagrams.** A state datagram's DATAGRAM frame carries at most 1,200 bytes: Species' 8-byte header (the update's tick and its baseline tick) and at most 1,192 bytes of records. The size is asserted at the sender against the largest datagram that MsQuic reports (`MaxSendLength`), which is 1,207 bytes at MsQuic's starting MTU of 1,288 bytes on IPv6; no state datagram therefore depends on path MTU discovery, and a state update larger than one datagram is split into self-decodable datagrams (ADR-086 item 3), never fragmented. **Overhead per state datagram: 89 bytes besides its records on IPv6 and 69 on IPv4**, computed from the framing, not measured: IPv6 40 (IPv4 20) and UDP 8; the QUIC 1-RTT short header 14 (1 flags byte, the 9-byte destination connection id that MsQuic generates without a server-id prefix, and the 4-byte packet number that MsQuic writes, the most that RFC 9000 §17.1 allows); the DATAGRAM frame's type and 2-byte length 3 (RFC 9221 §4); the AEAD tag 16 (RFC 9001 §5.3); and Species' header 8. ACK frames for the client's packets add about 7 bytes each, at most about 40 a second at the default largest acknowledgement delay of 25 ms (RFC 9000 §13.2.1), under 0.3 KB/s, which the model leaves out. The MVP's M4 measures the overhead (Confirmation). On an idle connection the client sends a QUIC keep-alive every tick period (MsQuic's `KeepAliveIntervalMs` = 100); the client shows that it waits for the server after 1 s without data and disconnects after 15 s; the server's idle timeout (`IdleTimeoutMs`) is 30 s, and it keeps the record of a departed connection for at most 10 minutes (DEC-205 item 9).
4. **Security and identity.** Every `QuicTransport` connection is secured by TLS 1.3 (RFC 9001) through MsQuic's Schannel build, without 0-RTT data, which Schannel does not offer and which could be replayed. Against spoofed-source amplification the server sets MsQuic's `RetryMemoryFraction` to 0, so a new address first receives a stateless Retry (RFC 9000 §8.1.2), smaller than the client's Initial packet that QUIC pads to at least 1,200 bytes; beyond it QUIC's limit of three times the bytes received holds until the address is validated (§8.1). Each server creates a self-signed ECDSA P-256 certificate at its first start; the client takes the certificate from MsQuic's certificate-received event (`QUIC_CREDENTIAL_FLAG_INDICATE_CERTIFICATE_RECEIVED`, with the operating system's chain validation off for the connection, because the certificate is self-signed) and pins it by the server listing (D5) or, for a server reached by its address, on first use with its fingerprint shown to the player, and refuses a changed certificate with a warning. Each player has an **identity key**, an ECDSA P-256 key pair created in the user's CNG key store at first launch, whose private half never leaves it; on the command stream at the handshake (item 6) the client signs a server nonce bound to the server certificate's fingerprint, so a signature cannot be relayed to another server. A server keeps a key registry: it registers a key at a steward's first join, a returning steward reclaims the settlement by it (ADR-086 item 5), and a steward who has lost the key is bound to a new one by the world host through the administration interface, recorded in the world record (ADR-087 item 8). No password and no credential travels in clear, and Species implements no cryptographic protocol of its own. Reachability for the first world-game milestone is the R14-clean baseline of O45: one UDP port mapped through the in-box UPnP NAT API, IPv6, and a manual address; there is no relay, so a host behind carrier-grade NAT is unreachable, and no identity across servers, until a provider is chosen with the storefront (O49).
5. **Messages.** Every message type has its own schema, versioned, in a bit-packed binary layout without field names, length-prefixed on a stream, with a hard limit on every count, length and depth; codecs are generated from the schemas (ADR-062). A malformed, oversized or unknown message is dropped and counted, never fatal (DEC-207 items 4 to 7); every parser is fuzzed in CI (ADR-069).
6. **Build and content identity at the handshake** (DEC-204, option A). The client sends its build identity (ADR-057) with its protocol version and its simulation version, and the content manifest hash (ADR-060) of its simulation-relevant and presentation content; the server refuses a different protocol, simulation or content with a reason that the client shows. The world names its world template and generator versions (WLD-009). Downloading content from a server (DEC-204 option B, for later modding) is a later record and needs no change to this handshake.
7. **Diagnostics and administration** (DEC-208, option B). Per connection: the measured round trip, jitter, loss and congestion window from MsQuic's connection statistics, the downstream and upstream rates against their budgets (ADR-086), the age of the newest state, the interpolation buffer, the reliable backlog and the rejected commands. Per server: tick wall-time percentiles against the budget and the deadline (ADR-080 item 6), each region's step time and bodies, battles in progress, bandwidth per region and per client, the owed ticks and the stalls of ADR-083, and the newest consistent cut. They are shown in the developer overlay, written to the server's logs (ADR-067), and published through the server's **administration interface**, an authenticated `species-admin` connection on the same transport with its own message schemas; the integrated host's tools, a dedicated server's operator console and every host command use only that interface (ADR-083 item 2), and every command on it is recorded (ADR-087 item 8). Every Debug build can route its connection through the **link simulator**, a development tool under `Tools/` that relays the connection's UDP datagrams on the loopback interface with added latency, loss, reordering and a rate cap (soak target 10 % loss with reordering); it never ships. Every server keeps a command journal of the last 10 minutes with the consistent cut before it, written out on a crash or at the world host's request, so that a defect reproduces on the same build (ADR-081 Level 1).

### Consequences

* Good, because community servers need no platform service and no library outside R14's allow-list, and the integrated server shares every line but the queue.
* Good, because Species writes no cipher, handshake, retransmission, flow control, congestion control (RFC 9002) or fragmentation: QUIC provides reliable ordered streams and per-datagram acknowledgements in one connection, which removes the reliability layer that option B would have made Species write and maintain, and a lost state datagram never blocks a command.
* Good, because a returning steward is recognised by a key that only that steward's machine holds, without an account, and a stolen signature is useless on another server.
* Good, because every parser is bounded and fuzzed, a build or content mismatch is a clear refusal, and an operator sees the same numbers as a developer.
* Bad, because `msquic.dll` ships beside the executable and is serviced by Species' releases, not by Windows Update, so the pin of ADR-089 follows MsQuic's security releases.
* Bad, because QUIC's congestion control also paces the state datagrams: on a congested link MsQuic delays them before Species' own cap of ADR-086 item 4 trims the update, which M4 and the remote-steward milestone measure.
* Bad, because the headers of a state datagram, 89 bytes on IPv6 and 69 on IPv4, are 7 % to 10 % of each crowd view's bandwidth and up to 39 % of the strategic view's 2.3 KB/s (`A2ServerBudget.py bandwidth`). On IPv4 they are 8 bytes fewer than option B's 77; the model takes IPv6's 89, which raises each view by 1 % to 2 % over option B's figures (a battle view 23.4 KB/s against 23.2). The figures are computed until M4 measures them.
* Bad, because without 0-RTT every connection and reconnection takes a full handshake, two round trips with the Retry of item 4: 300 ms at a 150 ms round trip, inside the rejoin target of 10 s.
* Bad, because players hosting behind carrier-grade NAT cannot be reached until a relay exists, and a player's identity is per machine until D5's service exists (O45).
* Neutral, because a dedicated server for a second operating system, a later ADR (O41), needs MsQuic's build for that system and its own key store; the protocol and the keys are standard.

### Confirmation

**Confirmed when** (amended 2026-10-19 for the MVP's milestones, O51 and O55): at the MVP's M4 (MVP-071), the headless server and the client connect over `QuicTransport` on the loopback interface; through the link simulator at 10 % loss and a 150 ms round trip for 30 minutes the client's world view freezes no figure for more than 2 ticks after a single lost datagram; the overhead per state datagram, measured from MsQuic's statistics over the same run, is within 5 bytes of item 3's 69 (IPv4 loopback) or 89 (IPv6 loopback); a client of another build or with an edited content file is refused with its reason; the integrated server runs the same session through `InProcessTransport` with identical per-tick hashes; and the fuzzer has run every message parser for 10⁷ inputs without a crash or an unbounded allocation. At the first milestone after the MVP that has remote stewards, 4 clients pass 30 minutes at 10 % loss and a 150 ms round trip; a client that changes the server's certificate, replays a signature to another server or claims a registered settlement with another key is refused (the identity key of O45 is not built in the MVP); a handshake from a spoofed address draws no reply larger than its request; and area D9's review of the identity flow is recorded.

## Pros and Cons of the Options

### A — a platform transport

* Good, because relay and NAT traversal come with it.
* Bad, because it ties community servers to a platform service and adds a third-party library outside R14's allow-list.

### B — an own datagram transport inside the operating system's DTLS

* Good, because it depends on nothing beyond the operating system, serves both stages and leaves the cryptography to a standard implementation.
* Bad, because its reliability, channels, fragmentation and robustness are Species' to build and test, Schannel stops at DTLS 1.2, and its reach stops at carrier-grade NAT without a relay.

### C — a stream for commands and datagrams for state

* Good, because a stream gives reliability for free.
* Bad, because a TCP stream blocks behind a lost packet, and two transports double the code and the security surface.

### D — QUIC through MsQuic

* Good, because one connection gives reliable streams without head-of-line blocking between them, unreliable datagrams with per-datagram acknowledgement, congestion control and TLS 1.3, all implemented and maintained by Microsoft, MIT-licensed, on the operating system's Schannel.
* Bad, because it adds a fourth package to R14's allow-list, a DLL that Species ships and services, and it needs Windows 11 or Windows Server 2022 for Schannel's TLS 1.3, which ADR-050's floor already meets.
