# Architecture decision records

This folder holds the engine-technology decisions of the Species reference library, one file per decision, `ADR-NNN-<slug>.md` (three-digit ids; owner decision O22, `AGENTS.md` §6), in the **MADR 4** format. Each record has YAML front matter (`status`, `date`, `decision-makers`) and the sections *Context and Problem Statement*, *Decision Drivers*, *Considered Options*, *Decision Outcome* (with *Consequences* and *Confirmation*), *Pros and Cons of the Options* and *More Information*.

- **Accepted** records state a decision the engine baseline is built on.
- **Proposed** records state a choice that is still open. Each one names the **default** the team proceeds with until the decision is confirmed or changed, and a **Confirmed when** line: the evidence and the milestone that turn it Accepted or replace it.
- A record flagged `owner-decision: blocking` in its front matter has no defensible default and waits for the owner. No baseline record carries that flag.

ADRs cover engine technology only. Game design lives in `reference/` and `decisions/`; the engine components in `architecture/components/` cite these records by number. The topics listed in [Deferred to the design phase](#deferred-to-the-design-phase) have no ADR: the Species design phase decides them (see [the vision brief](../../vision/species-vision-brief.md)).

## Index

The baseline holds ADR-001 to ADR-036, the engine runtime (renderer, textures, meshes, audio, input, UI, animation and VFX), and ADR-050 to ADR-077, the toolchain, the content pipeline and operations; ADR-078, the GPU resource factory, is the first record after the baseline; ADR-079 to ADR-089 are the solution strategy's (design area A2, `architecture/04_solution_strategy.md`), ADR-089 the record of the MsQuic package that the owner added to the allow-list (O44). ADR-037 to ADR-049 are unassigned and stay unused. A new record takes the next id after the highest existing one, whatever its topic (O22, `AGENTS.md` §6); the two baseline ranges are not a numbering policy.

#### 4 Direct3D 12

- **Agility SDK 1.619.6** (NuGet `Microsoft.Direct3D.D3D12`, D3D12SDKVersion 619, released 2026-09-14; 1.619 brought Shader Model 6.9). Export `D3D12SDKVersion` and `D3D12SDKPath = ".\\D3D12\\"` from `Species.exe`; never ship a preview SDK (latest preview: 1.721.3-preview) or `D3D12SDKLayers.dll`. A build check asserts that the exported number equals the packaged `D3D12Core.dll`. Every OS allowed by item 1.1 supports the Agility SDK. The `d3dx12.h` helpers and DirectX-Headers are not used (`AGENTS.md` R14). The dedicated server does not link Direct3D.
- **Feature level 12_1 minimum**, plus three capability checks: **Shader Model 6.6**, **Resource Binding Tier 3** and `D3D12_FEATURE_DATA_D3D12_OPTIONS1.WaveOps`; fail with a clear message if any is missing. 12_2 is not required: Species' look needs none of raytracing, mesh shaders, sampler feedback or variable-rate shading. Mesh shaders and VRS may be optional fast paths behind capability checks, never the only path. The crowd renderer is designed around compute culling plus `ExecuteIndirect`, which works at 12_1.
- **Shader Model 6.6 minimum**; compile every shader to `*_6_6` profiles. Bindless dynamic-resource access (`ResourceDescriptorHeap[]`, `SamplerDescriptorHeap[]`, root-signature flags `CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED` and `SAMPLER_HEAP_DIRECTLY_INDEXED`) is the only binding model. A Shader Model 6.7+ feature is used only behind a capability check with a 6.6 fallback, and only with an ADR. Query the highest supported model by looping downwards.
- **Enhanced Barriers** have been in the Agility SDK since 1.608.0 but are not a hardware or driver requirement: check `D3D12_FEATURE_DATA_D3D12_OPTIONS12.EnhancedBarriersSupported`. The frame graph expresses synchronisation in Enhanced-Barrier terms (sync, access, layout); the recording layer emits `Barrier()` when supported and translates to the `ResourceBarrier` API otherwise. Fence barriers (preview only) are not used.
- **Shader compiler: the `dxc` of the Windows SDK**, driven by `FXCompile` items in the project; Visual Studio uses `dxc` when a Shader Model 6 profile is selected, and writes each shader as a byte array in a header that the executable compiles in. `-HV 2021` explicit, `-enable-16bit-types` only where the capability is checked, warnings as errors, shader PDBs kept for PIX. No redistributable DirectX Shader Compiler and no `dxcompiler.dll` (`AGENTS.md` R14). Shader Model 6.6 has been available since April 2021, before the 10.0.26100 SDK series; the exact `dxc` version that SDK 10.0.26100.9457 installs is not published on Microsoft Learn and is recorded from the build machine. Shaders are written to compile under `-HV 202x` too (no effects syntax, no `interface`, no `uniform`).
- **Swap chain:** `DXGI_SWAP_EFFECT_FLIP_DISCARD`, 3 back buffers, `FRAME_LATENCY_WAITABLE_OBJECT` with a maximum frame latency of 1 or 2, `ALLOW_TEARING` when `CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING)` reports it. Windowed and borderless full screen only: Direct3D 12 has no fullscreen exclusive mode. Flip-model swap chains cannot be multisampled. VRR uses sync interval 0 with `DXGI_PRESENT_ALLOW_TEARING`; vsync uses sync interval 1; both are user options.
- **HDR: optional, off by default.** The SDR path renders to an 8-bit sRGB back buffer. The HDR path uses `R16G16B16A16_FLOAT` with scRGB (`DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709`), because the additive glow on black depends on blending and on values above 1.0; tone-map to the display from `IDXGIOutput6::GetDesc1`, and map UI to the SDR reference white level. #### 5 Content I/O and textures

- **DirectStorage is not adopted in v1** (latest stable 1.3.0, 2025-06-27; 1.4.0-preview2, 2026-06-16, adds Zstandard). Species' flat-shaded, vertex-coloured assets are few and small, so load time is dominated by parsing and GPU upload, and the dedicated server cannot use DirectStorage anyway. The runtime package format stores assets in independently compressed chunks of at most 256 KiB, aligned to 64 KiB, with a table of contents, so a DirectStorage back-end can be added behind the same I/O interface if terrain streaming at the strategic zoom level proves I/O-bound. No preview DirectStorage or GACL in any build. DirectStorage is not on the allow-list of `AGENTS.md` R14; adding its back-end needs an owner decision recorded as an ADR.
- **Pack compression: the in-box Windows Compression API** (`compressapi.h`, `Cabinet.dll`, from Windows 8), which exposes MSZIP, XPRESS, XPRESS with Huffman encoding and LZMS. Species uses **XPRESS with Huffman encoding** in buffer mode, one call per chunk of at most 256 KiB: a higher ratio than plain XPRESS, medium to high decompression speed and a low memory requirement; LZMS suits data over 2 MB, more than a chunk holds.
- **DirectXTex `may2026`** (2026-05-08; NuGet package `directxtex_desktop_win10` 2026.5.8.1, licence expression MIT, x64 static libraries; nuget.org marks the package deprecated in favour of the library's vcpkg port, and it still restores at its pinned version) is called from the Species asset cooker in the content build tool, a development tool that never ships (`AGENTS.md` R14); texconv is for manual inspection only. Cooking options are data stored next to each source texture. Always write DDS with the DX10 header, always generate full mip chains, always state the colour space. CI cooks BC7 with the software codec so that output does not depend on the build machine's GPU.
- **Formats:** colour and UI art `BC7_UNORM_SRGB`; normal maps (if any) `BC5_UNORM`; single-channel data (glow masks, darkening masks, height, ambient occlusion) `BC4_UNORM`; data that needs exact values stays uncompressed (`R8_UNORM`, `R8G8_UNORM`). No BC1 to BC3 in new content; BC6H only if HDR sky or light textures are added. Glyph atlases are never block-compressed. BC4, BC5 and BC7 are supported at every feature level from 11_0 up.

#### 8 Asset formats

- **Meshes and animation: glTF 2.0** (`.glb` for checked-in sources; right-handed, +Y up, front faces +Z, metres), cooked into Species' own runtime format; the runtime never parses glTF. A primitive without `NORMAL` has implicit flat normals, which gives the faceted look; `COLOR_0` (unorm8 RGBA) carries per-vertex colour. Allowed extensions: `KHR_materials_unlit`, `KHR_materials_emissive_strength`, `KHR_mesh_quantization`; everything else is rejected unless an ADR adds it. The content build tool's glTF importer validates every source against the specification itself (container, required properties, accessor and buffer-view bounds, component types, index ranges, extensions), because a tool dependency comes from NuGet only and no glTF validator is published there (owner decision O30, [ADR-019](ADR-019-mesh-source-format-and-cooked-meshes.md)). **Since owner decision O64 the mesh sources are CMO files** (`.cmo`, the Visual Studio mesh content pipeline's binary format; right-handed, +Y up, counter-clockwise front faces, as the owner's files measure), read by the content build tool's own CMO importer and cooked into the same runtime format; the glTF rules above no longer apply to sources ([ADR-019](ADR-019-mesh-source-format-and-cooked-meshes.md) amendment).
- **Every cooked texture is a DDS with the DX10 header** (`dxgiFormat`, sRGB-ness and array size explicit); the loader rejects any DDS without it.
- **Audio sources:** uncompressed WAV, **48 kHz**, 24-bit integer (or 32-bit float) PCM; mono for every positional sound, stereo for music and UI. **Runtime:** only formats that XAudio 2.9 decodes itself (16-bit PCM, 32-bit float PCM, 16-bit ADPCM and xWMA on PC): short, frequently triggered effects as 16-bit PCM at 48 kHz, fully resident; music and long ambiences as streamed **MS-ADPCM** (up to 4:1, 32 to 512 samples per block), encoded by the content build tool because the AdpcmEncode tool's distribution is not confirmed. xWMA is not used (its encoder's distribution is not confirmed either), and no third-party codec is used (`AGENTS.md` R14). The mastering format is the device default; XAudio2 converts sample rates.

#### 9 Text

- **Path:** `IDWriteTextLayout` for shaping, bidirectional text, line breaking and font fallback → a custom `IDWriteTextRenderer` that receives glyph runs → for each glyph not yet cached, `IDWriteFactory3::CreateGlyphRunAnalysis` with a natural-symmetric raster mode and `DWRITE_TEXT_ANTIALIAS_MODE_GRAYSCALE` → `CreateAlphaTexture` into a staging buffer → one coverage channel copied into an `R8_UNORM` atlas page.
- **Cache key:** font face, glyph index, pixel size (after DPI and the text-scale setting), subpixel x-offset quantised to a quarter pixel; LRU eviction by atlas page. No ClearType in the game UI. A distance-field atlas built from `GetGlyphRunOutline` is an option for world-space labels at the strategic zoom, not the baseline. Fonts ship with the game (licensed for embedding) in a custom font collection; system fonts are only a fallback for user-entered text. The headless server never touches DirectWrite.

#### 11 Crash reporting, packaging and code signing

- **Let WER handle crashes** and receive the data through the free **Windows Desktop Application Program** (requires code signing; data appears from 100 installed devices). Do not install a top-level exception filter that swallows crashes. Register the current log and settings files (`WerRegisterFile`), a small black-box ring buffer (`WerRegisterMemoryBlock`), and exclude personal data (`WerRegisterExcludedMemoryBlock`). Every Release build that the release procedure packages publishes its PDBs to a private symbol store and uploads its symbols to Partner Center; CI builds publish none until a symbol job is added (CI uploads the build log and the test results only). The build provides a `LocalDumps` registry file for test machines. The device-removed path writes DRED data into the same report. The dedicated server is a Windows build, so WER covers it too; where its reports go is a design-phase decision, and a third-party crash SDK is excluded by `AGENTS.md` R14.
- **One relocatable install directory** (`Species.exe` with its shaders compiled in, `WinPixEventRuntime.dll`, `D3D12\`, data packages, the GameInput redistributable as a prerequisite) that writes user data under `%LOCALAPPDATA%\<Studio>\Species\`, where `<Studio>` is the publisher-name parameter, and never beside the executable; every distribution format wraps that directory. The engine stays MSIX-compatible; the storefront choice is a design-phase decision. Whether the Agility SDK passes MSIX certification is not verified.
- **Sign every PE file and the installer** with SHA-256 and an RFC 3161 timestamp, in the release procedure, on Release builds only (CI builds Debug only). Preferred: Azure Artifact Signing if the publishing entity is eligible, otherwise an OV certificate in a hardware-backed or cloud key store; EV brings no SmartScreen advantage. Signing keys never live on developer machines or in the repository.
