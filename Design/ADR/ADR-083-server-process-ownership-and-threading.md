# Server process architecture: one headless server library, composition roots and lifetimes, state owners, region jobs, a deadline-paced tick loop and consistent cuts

## Context and Problem Statement

One server codebase runs integrated in the host's client and stand-alone on dedicated servers, behind the same transport interface, and the client never touches server state (O10, vision §5). The world is partitioned into regions from day one (O1, WLD-020), freezes while its server is not running (O4, O35), and keeps a stage-1 world running while the host's client stays open with its presentation suspended (PIL-077; for the MVP, O54 keeps it running in a background headless server process instead). The reference has one windowed process, process-wide state, an object reachable from everywhere, a single simulation thread, busy loops and a sequencer polled by whichever loop runs (DEC-221 to DEC-226). The deferred entries ask how the processes are composed and their state machines (DEC-221), who owns which state for how long (DEC-223), which threads run what (DEC-224), how the loops are paced (DEC-225) and how content is loaded and streamed (DEC-226). Process roles and the headless build (DEC-220) are area D1's; this record assumes its option A, separate build targets with a server library that links no presentation code. Under O21, O41 and `AGENTS.md` the dedicated server is a Windows build with a portable core until a later ADR decides another host.

How is the server built, composed, owned, threaded, paced and checkpointed, so that the integrated and the dedicated server are the same program?

## Decision Drivers

* One server library for the integrated server, the dedicated server and the test runner (O10, DEC-220).
* Every per-world and per-region object created and destroyed in one place, persisted without hidden state (DEC-223, DEC-251).
* Regions that step independently now and in separate processes later (O1, ADR-085).
* World time independent of any client's frame rate (DEC-220 item 9, DEC-225).
* Results independent of thread count and scheduling (ADR-081 Level 1).
* A restore after any crash, deliberate or not, that is consistent across owners.
* Operating-system code kept in one layer, the only part that a server for another operating system would replace.

## Considered Options

* A — composition roots per process role with explicit lifetimes and state machines; one state owner per region, per world and per skirmish match; region steps as jobs; a fixed-rate server loop that sleeps to its deadline; consistent cuts
* B — a service registry with run-time lifetime scopes; a fully parallel per-tick job graph across systems
* C — the reference structure: one root object, process-wide state, one simulation thread, client-driven stepping

## Decision Outcome

Proposed option: "A". **Default while Proposed:** the decision below.

1. **The server library** is headless C++23 and a Windows build with a portable core (O21, O41). It reaches the operating system (files, threads, the clock of ADR-074, cryptography and the key store) only through the platform layer (PLT), and the network only through MsQuic behind the transport (ADR-088, ADR-089); no header of the server or simulation libraries includes a Windows header, and no persisted or transferred data uses a Windows-only format or codec, so a server for another operating system, which a later ADR may add (O41), replaces the platform layer, the in-box services it wraps and MsQuic's build for that system, never the simulation. The library holds the state owners, the tick loop and its worker pool, command validation (ADR-087), interest management and replication (ADR-086), the persistence interface, the server API of O6 and the AI runtime. The client links it for integrated hosting and for skirmish; the dedicated server and the headless test runner link it with no presentation code (DEC-220 option A, D1).
2. **Composition roots** (DEC-221, option A). Each process role has one composition root that creates every service in a documented order and destroys them in the reverse order (PLT-038, PLT-043); no service is reached through a global. The lifetime scopes are: process; server run (one world from its opening to its freeze, or one skirmish lobby to its results); world (persisted across server runs); region; battle (inside its region); match (a skirmish match world, `MatchWorld`); client session (one connection of a client to a server); connection (on the server, one client). The integrated server's root is a child of the client's root, composed through one header of the server library, `IntegratedServer.h`, which offers only start, stop and a `Transport` endpoint; the client executable may include that header and no other server header (ADR-084 item 2), and every host tool reaches the server through the administration interface (ADR-088 item 7). Starting and stopping it never tears down the client, and stopping it freezes the world (O4, PIL-131).
3. **State machines.** The client: Boot → FrontEnd → Connecting → Loading → InWorld or InMatch → Leaving → FrontEnd, with quit accepted in every state and one teardown for every exit (PLT-042); the integrated host's client has, in InWorld, the presentation-suspended mode of PIL-077. A world server: Stopped → Opening (load and validate the world, every region) → Running → Freezing (the final cut and the freeze record) → Stopped. A skirmish server: Lobby → Loading → Match → Results → Lobby. A state machine's transitions are the only way a lifetime scope begins or ends.
4. **State owners** (DEC-223, option A with B inside it). One owner holds every mutable simulation value of its scope: a region owner (`RegionSimulation`) per region, holding its settlements, figures, structures, battles, grids and routes; one world owner (`WorldSimulation`) per world, holding the world tick, the keys of ADR-082, the Cladans' grievances and relations, the register of claims and declared attacks, the battle slots, the keeper (WLD-125) and the world record; and one owner per skirmish match (`MatchWorld`). Simulation code holds no mutable static state (R-SIM-730). Each owner may store its objects in typed pools or a component store; either way it serialises canonically, with no hidden state, and it is the unit of persistence, of hashing (ADR-081) and of hand-over (ADR-085).
5. **Identity.** Every simulated object of a world has a stable 64-bit id, unique in the world for its life: the creating owner's id in its high 16 bits and that owner's creation counter in the low 48 bits; the counter is owner state and is part of every cut. Messages, persistence, replication, random draws (ADR-082) and every total order of ADR-081 item 2 name objects by stable id; pool slots and generational handles (R-SIM-131 to R-SIM-143) stay inside their owner.
6. **Threads** (DEC-224, option A). A server has a tick thread and a worker pool. In each tick the tick thread delivers the messages of the previous tick (ADR-085), runs every region owner's step as one job (regions in parallel, each serial inside in the reference update order of ADR-079), then the world owner's step, then the replication encoding per client as jobs, then, on a cut's tick, the copy of item 9. Network I/O runs on its own threads behind lock-free queues (DEC-207 item 9); the store and logging run on their own threads (ADR-067). Inside one region step, a phase that reads the previous state and writes per-object outputs (the Workers' searches first) may be split into parallel jobs merged in a fixed order; this is the first remedy when a measured region step exceeds half its budget (ADR-080), because it restores the step without changing a rule. The integrated server runs its tick thread and at most 2 workers (ADR-080 item 7). The result of every tick is that of the serial order at any thread count (R-SIM-732).
7. **Pacing** (DEC-225, option A). The tick loop schedules tick *n* at the start time plus *n* tick periods and sleeps to that deadline; it never busy-waits and never takes its rate from a client frame. A tick that overruns lets the next start at once; the loop then runs owed ticks at most twice per period, up to 20 owed ticks (2 s). Beyond 20, the schedule is anchored again at the present, and the real time lost is not world time (O4); a gap of 10 s or more is recorded as a freeze with the cause "server stall" (PIL-131). In skirmish, game speed is tick scheduling (R-SIM-548): within each tick period the server runs as many world ticks as the accumulated game speed allows, carrying the fraction, at most 2 per period (Time Rush's 2.0), and keeps one command frame per period (R-SIM-549), so a match's CPU and its updates per period double for the 151-tick hold of a Time Rush; DEC-264 is area D2's. Clients render at their own rate from replicated state (ADR-084) and never step the simulation.
8. **Loading and streaming** (DEC-226, option A for the world, B allowed for skirmish). A world opens by loading its records and its baked terrain chunks (WLD-166) on the worker pool with progress reported to the world host, and runs only when every region is loaded, so that every region steps the same tick. World generation and extension (WLD-165) run as background jobs, never inside a tick. A client streams terrain chunks by digest and content packs asynchronously with progress and explicit completion signals (DEC-226 items 2 and 3, ADR-086 item 5); a skirmish may show a blocking loading view. No load pauses a region, and the server keeps its clients' connections alive through every load.
9. **Consistent cuts.** At the end of tick *t*, when a cut is due, every owner whose state changed since its last cut copies its state, its id counter and the messages it produced in tick *t* for tick *t* + 1 into a buffer (a memory copy on the tick's workers: 1.3 ms in reference cores for a world of 200 at its stress case, spread over the workers); the store thread serialises the buffers canonically and writes the set, with the unchanged owners' earlier record sets, as one transaction whose manifest names tick *t* and is written last. A restore loads the newest complete manifest, re-delivers its messages and resumes at tick *t* + 1, so no cross-owner event is ever half-restored and no stable id is issued twice. A cut is due every 600 ticks (60 s of world time), and in an integrated world every 100 ticks (10 s) while a battle runs, so a host who ends the process can wind a battle back at most 10 s (1.4 MB every 10 s, 141 KB/s, at 16 stewards); freezing writes a final cut and loses nothing. Every restore after an unclean stop is recorded in the world record with the world time it lost and whether a battle ran (PIL-131, PIL-132), and every manifest extends the world's hash chain (§4.3.1 of the solution strategy), so the record cannot be removed unseen. The store is Species' own journaled record store in plain C++ over the platform layer's files (O42; solution strategy §4.3.1 items 3 and 10); its schema, migration, backups and rollback are area D4's (DEC-250, DEC-251).

### Consequences

* Good, because the integrated server is literally the dedicated server's library, started through one header by a child root, so O10 holds by construction.
* Good, because region steps are independent jobs with messages between ticks, which is the same model across processes (ADR-085).
* Good, because world time depends only on the server's own loop, at every pace and in every stage.
* Good, because a crash at any moment restores one consistent world, and a deliberate kill gains at most 10 s of a battle and leaves a record.
* Bad, because every service and owner must be wired explicitly in its root, and every object needs a stable id from its creation.
* Bad, because a region's step is single-threaded until measured otherwise, so one region's cost is bounded by ADR-080's region step budget rather than by the core count.
* Neutral, because skirmish keeps the reference's single match world, now as one owner of the same server.

### Confirmation

**Confirmed when** (amended 2026-10-19 for the MVP's milestones, O51 and O55, and 2026-10-20 for item 7's bound, O68): the MVP's M0 builds the headless server with no presentation library linked and a client that includes no server header but `IntegratedServer.h`, and the headless server runs its test world; at M1, a forced stall of 2 s catches up within 2 s at most twice the rate, and one of 30 s is recorded as a freeze; by M4, quit is tested from every state of the client's and the world server's state machines, and a forced kill at every phase of a battle's end restores a world whose hashes equal those of a run stopped at the restored save's tick (the MVP's snapshot of MVP-075 stands in for the consistent cut); and at the first milestone after the MVP with more than one region and with skirmish, a world and a skirmish match stepped in one process give the same per-tick hashes as each stepped alone (DEC-223 item 4), and the forced-kill test covers every phase of a crossing with the consistent cut of item 9.

## Pros and Cons of the Options

### A — roots, owners, region jobs, a deadline loop, consistent cuts

* Good, because ownership, order, pacing and restore are explicit and testable, and the region split scales across cores and processes.
* Bad, because a region's step uses one core until a phase is split.

### B — a registry and a full job graph

* Good, because it can reach a higher throughput per region.
* Bad, because order-dependent rules become hard to keep and to verify, and the registry hides dependencies.

### C — the reference structure

* Bad, because it contradicts the headless server, the separation of O10 and a world time independent of frame rates.
