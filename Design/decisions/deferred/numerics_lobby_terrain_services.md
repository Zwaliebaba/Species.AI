# Deferred decisions: numeric model, lobby and sessions, terrain runtime, services and persistence

This file holds the design-phase decisions on five topics that the reference library deliberately does not specify: the simulation numeric model, the lobby and session protocol, the terrain runtime model, identity, entitlement and discovery services, and saves and persistence. The vision brief (`vision/species-vision-brief.md`) decides the world architecture for these topics: an authoritative server, integrated first and dedicated later; community hosting; a region-partitioned world; world state in a database; and growth from 16 to 200 or more players per world. Each entry was written **Open**, to be decided in the design phase; design area A2 resolved DEC-240 to DEC-242 on 2026-10-19, after owner gate B (ADR-081 and ADR-082), and the others stay Open for the areas that the decision triage names. Its "Specified behaviour" names the reference default that applies until then. "Constraints and lessons" lists the failure modes to avoid and the figures, with units, that the decision needs. "Reference behaviour" summarises the roles and properties of the reference mechanism. The related deferred topics are the networking model (`networking.md`) and the process architecture, tick rate and build order (`process_tick_and_roadmap.md`), both in this folder.

## Numeric model

### DEC-240 Simulation numeric model and determinism scope

- Status: Resolved
- Affects: R-SIM (`reference/12_simulation_model/`: tick timing, entity model, randomness and integrity); TER (`architecture/components/terrain/`); DAT (`architecture/components/data_schemas/`); BLD (`architecture/components/build_tooling_and_distribution/`: simulation library build settings); DBG (`architecture/components/diagnostics_test_and_performance/`: replay and golden-hash tests); PLT (`architecture/components/platform_layer.md`: the floating-point environment of the threads that run simulation code); DEC-241, DEC-242, DEC-246, DEC-251; `networking.md`.
- Specified behaviour: The reference library states simulation rules in integer ticks and world units (wu) and fixes no numeric environment. Until the design phase decides, the default is the reference model: simulation state in IEEE-754 binary64, every transcendental and square-root result rounded to binary32 and widened back, and bit-identical results required for every simulation input on every participant.
- Options: A — the reference model: binary64 state with binary32-rounded transcendental results, relying on every participant running one build with one floating-point control state; B — strict IEEE-754 binary64: simulation code in its own library, built with the compiler's strict floating-point model (no contraction, no reassociation, no auto-vectorisation of simulation code), an own deterministic maths library for every transcendental function, and the floating-point control state asserted at every tick entry and in every simulation worker; C — fixed point: integer simulation state (for example Q32.32 positions, integer ticks, table-driven or CORDIC trigonometry, integer square root), bit-exact across compilers and architectures by construction; D — no cross-process bit-exactness: the authoritative server's state is the only truth, clients present replicated state, and reproducibility is required within one build only (replays and regression hashes).
- Recommendation: B, scoped by the networking decision. The vision makes the server authoritative, so bit-exact agreement between processes is needed only where the networking model re-simulates instead of transmitting state (client-side prediction of crowds, deterministic battle replication to save bandwidth), where replays must stay valid across builds, or where one battle must give identical results on the integrated server and on the dedicated-server build. B covers all of these when every build compiles the same simulation source under the strict model, and it keeps binary64 headroom for a large world. First declare the determinism scope per data path: which results must agree, and between which builds. Hold C in reserve, and adopt it from the start if a later ADR adds a second architecture or a second compiler (O21) that must interoperate bit-exactly within one battle and the cross-build hash tests of B fail. Do not keep option A's binary32 rounding of transcendental results: it narrows the dependence on the maths library but never removes it.
- Resolution (2026-10-19, design phase, area A2, after owner gate B of 2026-10-18): option B, strict binary64, scoped by three determinism levels: Level 1 (one build, any CPU, any thread count) required and tested, Level 2 (every executable of a release) required for world generation and holding by construction between the integrated and the Windows dedicated server, Level 3 not provided; own deterministic maths functions, an asserted floating-point environment, fixed-width types and total orders; option C held in reserve with a named trigger; the dedicated server is a Windows build with a portable core (O41) (ADR-081 items 1 to 4, 6, 7 and 9). The MVP defers the own maths functions and Level 2 (MVP-093).
- Constraints and lessons:
  1. **What must be bit-exact.** Under command-stream re-simulation (every participant simulates from the same ordered commands), every value that feeds simulation state must be identical on every participant: positions and velocities, timers, stat-derived values, terrain heights and normals, random draws, and every comparison derived from them. A 1-ulp difference flips a comparison (a walkability threshold, a range test, a timer test), and the participants diverge without any error. Presentation results (rendering, audio, user interface, cosmetic particles) never need to agree.
  2. **Why: transcendental functions.** Sine, cosine, tangent, arcsine, arccosine, arctangent, exponential, logarithm and power are not correctly rounded by platform maths libraries. Their results differ in the last ulps between library versions, between compilers, and between the CPU-dispatched code paths of one library on different CPUs. A model that needs bit-exactness implements them itself (polynomials or tables evaluated in a fixed order) and bans platform transcendental calls in simulation code, enforced by a lint rule.
  3. **Why: rounding.** IEEE-754 addition, subtraction, multiplication, division and square root are correctly rounded under round-to-nearest-even, so they are reproducible only when every intermediate result is rounded to its declared type. On x64 every SSE2 operation rounds to its declared type (`AGENTS.md` R16), and Direct3D 12 device creation leaves the floating-point environment unchanged. The remaining hazards are: a rounding or exception control state that a third-party component changes as a side effect; the flush-to-zero and denormals-are-zero settings; and worker threads that never set the control state. The control state must be set and asserted at every tick entry and in every worker that runs simulation code, and no third-party code may run inside a tick; gameplay is computed only by the CPU simulation (DEC-654).
  4. **Why: ordering.** Floating-point addition and multiplication are not associative. Fused multiply-add contraction, reassociation under a fast floating-point model, auto-vectorised reductions in a different order, and any change in evaluation order all change results. Simulation expressions are evaluated in the order written, and reductions over collections iterate in a defined index order.
  5. **Rounding transcendental results to binary32 is not a guarantee.** If two libraries' binary64 results straddle a binary32 rounding midpoint, they still round to different values. The chance is about 2⁻²⁹ per call for a 1-ulp disagreement, and k·2⁻²⁹ for k ulps. Over 10⁸ to 10⁹ transcendental calls per match this is rare, but not impossible.
  6. **Mixed precision inside the model.** Rounding square-root and trigonometric results to binary32 gives every length, unit vector and rotation about 7 significant decimal digits, although positions are binary64. A handful of timer and cache fields are binary32, so every assignment to them rounds. A Species model chooses the precision of each simulation quantity deliberately and documents it.
  7. **Build identity is a simulation input.** Two builds of one version can use different floating-point models. A handshake that compares only a version string cannot tell them apart and lets them play together. Whenever bit-exactness is required, the session handshake compares a build or numeric-model fingerprint (DEC-245).
  8. **Target platforms.** Species builds for Windows x64 only, the dedicated server included (O21, `AGENTS.md` §3); there binary64 basic operations are correctly rounded and reproducible, and the remaining sources of divergence are compiler transformations, CPU-dispatched maths library paths and the floating-point control state. An ARM64 build or a dedicated-server build for another host (vision §6 item 10) each needs an ADR that changes O21, and each would bring a second compiler or maths library into the choice; if cross-architecture play is ever planned, fixed point from the start is the safe choice.
  9. **Verification from the first month.** Replay a corpus of recorded battles on at least two CPU generations from each of two x64 vendors, and on every server build, and compare per-tick state hashes. A test that adds a cosmetic effect must leave the simulation hash unchanged.
  10. **State transfer needs exact serialisation.** Where the authoritative server sends or stores state instead of re-simulating it (replication, region hand-over between server processes, the world database of DEC-251), values must round-trip exactly: a binary encoding with a defined byte order, or a shortest round-trip decimal form. A fixed number of decimals is never enough; the reference displays decimal lobby values with two decimals.
  11. **Fixed point is a feasible fallback.** A signed 64-bit fixed-point type with 128-bit intermediates, and table-driven sine and arcsine generated offline, is a known-feasible design. Conversion from floating-point input is not portable unless it runs once, at load or build time, through one portable, correctly rounded parser.
- Reference behaviour: The reference simulation holds geometry and almost every object field in binary64. A few timers and query-cache fields are binary32, and some simulation decisions use binary32 locals. Every sine, cosine, tangent, square root, power, exponential, logarithm, arcsine, arccosine and arctangent result passes through a wrapper that rounds it to binary32 and widens it back; there is no wrapped form of the two-argument arctangent, floor or modulo. The rounding mode is never changed. Agreement between participants rests on every participant running the same build; nothing in a session verifies this.

### DEC-241 Numeric semantics that reference rules depend on

- Status: Resolved
- Affects: R-SIM (`reference/12_simulation_model/03_entity_model_and_identity.md`, `05_space_routing_and_physics.md`); R-UNIT (`reference/02_units/leader_and_formations.md`: formation volley timing); R-BLDG (`reference/03_buildings_and_world_objects/`: turret aim cone, Beam Dish yaw speed); DAT (`architecture/components/data_schemas/`: numeric field types and parsing); R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: lobby numeric values); PLT (`architecture/components/platform_layer.md`: the maths library, PLT-137, PLT-138); DEC-240.
- Specified behaviour: The reference documents state each rule in integer ticks and wu. Where the observable result of a reference rule depends on a rounding, truncation, tolerance or degenerate-input result, the reference semantics listed below are the default.
- Options: A — reproduce the reference semantics exactly, including the binary32 rounding of transcendental and square-root results and of simulation-feeding data fields; B — keep the observable rule semantics (truncation toward zero, degenerate-vector fallbacks, tolerance values) as explicit Species rules with acceptance vectors, and drop incidental rounding (binary32 transcendental results, binary32 fields and locals); C — define every numeric semantic afresh for Species.
- Recommendation: B. Reference tuning depends on a few numeric behaviours that can be stated as rules and tested with vectors: integer truncation, degenerate-vector fallbacks and tolerance values. Incidental binary32 rounding adds reproducibility risk and costs precision without carrying any rule. Each kept semantic becomes a requirement, either in reference/12 or in the Species maths library specification, and every timer becomes an integer tick count.
- Resolution (2026-10-19, design phase, area A2, after owner gate B of 2026-10-18): option B. The observable semantics that reference rules depend on (truncation toward zero, the degenerate-vector and degenerate-query results, the tolerance values, integer tick timers) stay explicit rules with acceptance vectors; the incidental binary32 rounding is dropped from simulation rules, while the terrain generator keeps the rounding of TER-065 (ADR-081 item 5).
- Constraints and lessons:
  1. **Integer conversion.** Converting to an integer truncates toward zero, independent of the rounding mode. The sign of zero is +1.
  2. **Stat representation.** DEC-090 (Resolved) decides it, not this entry: actor stats are floating-point values, and the speed multipliers ×2, ×1.5, ×0.75 and ÷2 apply exactly (R-SIM-145, R-SIM-707, R-UNIT-011). In the reference they are unsigned 8-bit values, so the multipliers truncate and a stat value above 255 in the data has no defined result (the reference data holds values of 350 and 500); that behaviour is option B of DEC-090. Schema validation rejects a stat outside its range (DAT-262).
  3. **Accumulated timers.** A countdown written as "subtract 0.1 per tick, stop at or below 0" drifts in binary64, because 0.1 is not representable, so some durations take one tick more than decimal arithmetic suggests. The resulting counts are: 1.0 → 11 ticks, 3.0 → 30, 10.0 → 101, 15.0 → 151, 5.0 → 51, 45.0 → 450, 1.5 → 15, 0.5 → 6, 4.0 → 40, 30.0 → 300, 0.2 → 2, 1.2 → 13. Integer tick timers resolve this, and the 11-tick mode second stays an explicit constant (DEC-002). Every simulation duration is stated in ticks.
  4. **Formation volley timing.** A Leader's formation member fires on ticks where the integer part of fmod(10 × game time + formation index, formation size ÷ 4) is 0, with ÷ 16 instead of ÷ 4 under Fury. The game time is converted to binary32 first, so the result depends on the last bit of an accumulated value. A formation of fewer than 4 members makes the modulus smaller than 1, so every member fires every tick. Species states this rule on the integer tick counter.
  5. **Gameplay angles and lengths.** The turret aim angle uses a binary32-rounded arccosine against a fire cone of 0.3 rad; the Beam Dish yaw speed uses a rounded square root; a carried structure's heave uses the sine of the network time; turret target wobble uses rounded trigonometry, and the same rounded trigonometry drives the Supply crate sway and the dust vortex in simulation paths. Under option B these use the Species maths library at full precision, and acceptance vectors pin the results.
  6. **Degenerate vectors.** Normalising a 3-vector requires a squared length above 10⁻¹⁰, otherwise the result is (0, 0, 1). Normalising a 2-vector requires a squared length above 0, otherwise the result is (0, 1). Setting the length of a vector whose magnitude is within 10⁻⁶ of 0 sets only the x component. Normalising the horizontal part of a vertical vector gives non-finite components. Species defines every degenerate result and never produces a non-finite value. The obstacle push of `reference/12_simulation_model/05_space_routing_and_physics.md` R-SIM-382 relies on the set-length rule: at a structure's base point the zero-length push becomes a push along x, so the push loop ends; any Species degenerate rule keeps a non-zero push direction there (DEC-014). A structure facing of zero length is normalised by the same rules (DEC-968).
  7. **Division by a scalar** multiplies by the reciprocal (one division and three multiplications), which is not bit-identical to three divisions. The Species maths library states which form it uses.
  8. **Tolerance equality.** 3-vector equality compares each component with an absolute tolerance of 10⁻⁶; 2-vector equality compares in binary32 against 1.19 × 10⁻⁷; scalar near-equality uses 10⁻⁶. Tolerance equality is deterministic but not transitive, so it is never used for ordering, sorting, hashing or set membership.
  9. **Matrix conventions.** The 3×3 rotation type multiplies a vector from world to local space, and the 3×4 type (`Mat3x4`) from local to world space; a matrix product applies the left operand first. The Species maths library has one documented convention.
  10. **Degenerate geometric queries.** In the reference, inverting a singular transform, the distance between parallel rays and the intersection of a segment with a parallel ray have no defined result, and the finiteness check accepts NaN; a ray–triangle hit may lie behind the ray's start, because the hit range bounds the length of the (t, u, v) vector rather than t, which terrain picking relies on (TER-017). Species queries reject degenerate input explicitly, and the finiteness check rejects NaN and both infinities (PLT-137 item 6, PLT-138).
  11. **Ordering guards.** Comparisons use values of their declared type under `/fp:precise` (`AGENTS.md` R16): the squared length before normalising, and the synchronised random values of the tree offspring height, the spider pounce factor and the Seed Pod tumble force, are compared as stored. The draw order of a random vector's components is x, then y, then z. Species gets the rest from the strict floating-point model of DEC-240 and from the one-draw-per-statement rule of DEC-242.
  12. **Parsing simulation data.** Integer fields accept an optional sign and decimal digits, stop at the first non-digit, give 0 for an unparsable token and do not detect overflow. Decimal fields are parsed to binary64; simulation-feeding decimal fields are then rounded to binary32 and widened back, while a few fields keep full binary64 precision (the Control Zone size and the priority modifier of a bot navigation node). The terrain maximum-height field is binary32 but reaches only presentation and the editor. The decimal parser is platform dependent. Species parses every simulation-feeding number with one platform-independent, correctly rounded parser, rounds it once to the simulation type, and rejects malformed and out-of-range tokens at build time.
  13. **Lobby numeric values.** Decimal lobby values are displayed with two decimals, parsed to binary64 and then rounded to binary32. Species lobby values are integers or fixed-point values with stated ranges, validated once by the authority (DEC-243).
- Reference behaviour: The reference maths layer provides binary64 2-vectors, 3-vectors, 3×3 and 3×4 matrices and planes, with rotations built from the binary32-rounded sine and cosine. It supplies degenerate-input fallbacks for normalisation, tolerance-based equality, reciprocal-multiply division and truncating integer conversion. A small set of simulation rules (formation volley timing, turret aim, stat multipliers and accumulated timers) depends observably on these semantics, while most others depend on them only through ordinary arithmetic.

### DEC-242 Simulation random generator algorithm and stream derivation

- Status: Resolved
- Affects: R-SIM (`reference/12_simulation_model/07_randomness_and_integrity.md`); DBG (replay and simulation-hash tests); TER (the private per-tile generator); DEC-240, DEC-246, DEC-251; `networking.md`.
- Specified behaviour: reference/12 specifies the draw discipline: one synchronised simulation generator for all gameplay randomness (`SimRng`), separate presentation generators for cosmetic draws (`FxRng`), a fixed draw order, and no presentation, audio or user-interface code drawing from the simulation generator. Until the design phase decides, the default is option A with PCG32: one sequential stream, owned by the match world and seeded once per match from the match seed, using PCG32, the published 32-bit-output PCG generator on a 64-bit state, with its published seeding procedure and stream 0. Golden hashes recorded under the default are valid within one build (DBG-147) and are recorded again, in a reviewed change, when this entry is decided.
- Options: A — one sequential stream per match or world, as in the reference structure, using a current generator (PCG32 or xoshiro128++), owned by the match world and passed explicitly; B — counter-based sub-streams: each draw is hash(seed, region, system, entity, tick, draw index), so adding a draw in one system does not shift any other; C — one sequential stream per system, each seeded from the world seed.
- Recommendation: B for both the world and skirmish. In a persistent, region-partitioned world a single sequential stream couples every region and system: one extra draw anywhere shifts every later draw everywhere, so replays break across patches, and region hand-over and the calibration of the abstract economy model against the full simulation (vision O3) become hard to reproduce. A counter-based generator is stateless, so only the seed needs persisting (DEC-251), and every entity's draws are reproducible on their own. Keep one presentation generator per thread, unreachable from simulation code.
- Resolution (2026-10-19, design phase, area A2, after owner gate B of 2026-10-18): option B, counter-based values: a simulation draw is SipHash-2-4 of a secret 128-bit simulation key over the domain, the purpose, the subject's stable id, the tick and the ordinal; world generation keeps `Mix64` over the public world seed (WLD-161); the order of a tick's senders is the same keyed function; presentation generators are PCG32 instances per consumer (ADR-082). Implemented in the MVP by MVP-093.
- Constraints and lessons:
  1. **No gameplay draw outside the simulation.** In the reference, no draw from the simulation generator occurs in user-interface, rendering or audio code. Keep that property and enforce it: cosmetic code cannot include the simulation generator's header, and a test that adds a cosmetic particle checks that the simulation hash is unchanged.
  2. **Never share a generator across purposes or threads.** In the reference, a presentation generator that audio, terrain colours, tree geometry and a network registration thread all share also feeds a simulation input (tree hit spheres), and it is not thread-safe. Any generator whose output reaches simulation state belongs to the simulation and is never shared with presentation code or background threads.
  3. **Draw order inside expressions.** Argument evaluation order is unspecified in C++, so a random vector built from three draws in one call has no defined order unless the code fixes it. The reference fixes it with marker types (x, then y, then z). Species: one draw per statement; no draws in constructors, argument lists or variable-length rejection loops; lint-enforced.
  4. **Seeding and recording.** The authority seeds the generator once per match (and once per world), and the seed is recorded in the replay and in the persisted world.
  5. **Terrain uses a private generator.** Each terrain tile owns a private generator, re-seeded from its tile seed at the start of every generation, so the terrain is independent of call history and of every other consumer (DEC-246). Any runtime procedural content keeps that property.
  6. **Divergence detection needs a real state hash.** A short generator-position value is too weak to detect divergence; detection belongs to the networking model (`networking.md`).
- Reference behaviour: The reference draws all gameplay randomness from one global synchronised generator, seeded once per server session, which is once per match. It offers integer, unit-fraction and signed-fraction draws. Cosmetic consumers use separate generators, terrain tiles use private per-tile generators, and a separate shared generator serves several presentation systems. The draw order within vector construction is fixed by marker types.

## Lobby and sessions

### DEC-243 Lobby authority and the match-setup state

- Status: Open
- Affects: R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: lobby page, ready-up, countdown and grace period); R-MODE (`reference/01_skirmish_rules_and_modes/README.md`: match options); R-SIM (`reference/12_simulation_model/06_teams_and_player_commands.md`); UI (`architecture/components/ui_framework/pages_and_screen_recipes.md`); DEC-241, DEC-244, DEC-245; `networking.md`.
- Specified behaviour: reference/09 specifies the lobby page, ready-up, the countdown and the grace period, and which controls the host and the joining players see. Which participant may change each setting is enforced only by the user interface. The default state model is the reference's: every lobby change is an ordered command that every participant applies, each option carries a version number, and a joining player replays the whole command history.
- Options: A — the reference model: lobby changes as ordered commands relayed to everybody, per-option versions, and full-history replay on join; B — authority-owned lobby state: the authoritative server (integrated or dedicated) owns the match-setup state, validates every lobby command (the sender's role and ownership, and the value's range), and publishes one atomic, versioned snapshot after each accepted change, while a joining player receives the current snapshot; C — B, with discovery and invitations delegated to a platform lobby service (DEC-249) and only the match-setup state held by the server.
- Recommendation: B, or C where a platform lobby is adopted under DEC-249. It follows the authoritative-server constraint of the vision (§5), removes every client-side authority failure listed below, and bounds join time by the snapshot size instead of the history length. It also serves both the skirmish mode, which runs on the same netcode as the world (O8), and joining the world: a persistent world has no lobby phase, but settlement claims and server settings need the same validation. Keep the ordered command stream for the in-match command log only, so that replays still come at no extra cost.
- Decide by: design phase
- Constraints and lessons:
  1. **Authority is client-side.** The server relays every option, start and ready command from any connected client without checking the sender; only the user interface limits editing to the host. A modified client can therefore change the mode, the map, the mode parameters and the bot difficulty, start the match, or toggle another player's ready flag. Only kicking is truly host-only, because it calls the host's own server object.
  2. **Missing fields must fail.** Option commands carry no team field. The relay check reads the missing field as a default placeholder byte, which passes the "sender has a team" test. A missing or malformed field must fail validation, never default to a valid value.
  3. **Start.** The start command is accepted from any client; only a second start in the same match is dropped. Under the reference rule, the match starts automatically when every human player is ready.
  4. **Range checks belong to the authority.** Each receiver range-checks values on receipt, and the bot-difficulty check accepts one value past the last level (corrected by DEC-077). Species validates once, at the authority, against stated inclusive bounds.
  5. **Per-option versions.** Every option, and every element of the two 64-entry arrays (mode parameters and research levels), carries a version. A request carries the sender's local version + 1; a receiver applies an update only if its version is greater than the stored one, and then stores it. Versions reset to 0 when a client joins. Conflicting simultaneous edits resolve as "first in the stream wins", which is correct only because one sequencer orders every command. A single version for the whole lobby state, owned by the authority, is simpler.
  6. **Bursts and half-applied states.** Choosing a mode sends one command per mode parameter, up to 64 in one frame. On receiving a mode change, every participant zeroes all parameters and research levels before the defaults arrive. Species applies a lobby change as one atomic update that no observer sees half-applied.
  7. **No user-interface dependencies in state handlers.** Turning co-op on clears every team colour and the locally requested colour; turning it off restores the previous colour through a front-end object that may not exist. Lobby state handlers must not depend on user-interface objects.
  8. **History replay is unbounded.** A joining player replays every lobby command from the first one (options, teams and chat) and, if the match has started, every tick since then (DEC-244 gives the figures). Snapshots bound this.
  9. **Repeated requests.** While connected with a team, a client re-sends its team name at most once per second while it differs from the confirmed name, and its colour every 0.1 s while it differs from the confirmed colour (not in co-op or Siege, except at the main menu). It sends its achievement mask every 60 s, and the seasonal-theme flag once. Repeating idempotent requests works only with an authority that acknowledges them.
  10. **What the match setup needs from the session:** the mode; the map, chosen by map id; the mode parameters (64 entries); the research levels; the bot difficulty (easy, standard, hard); the co-op flag; the single-round Siege flag; the basic-crates-only flag; a per-slot team status for 6 slots, which is written but never read; per slot, the owner, kind (local player, remote player, bot, spectator, unused), name and colour; the ready flags; chat; spectator conversion; achievement masks; the seasonal-theme flag; the password; and start. Selecting a mode assigns every mode parameter its default, and selecting a map sets the time-limit parameter.
  11. **Unknown messages.** An unknown or malformed lobby or session message is rejected and logged; it never terminates the process.
  12. **The integrated server uses the same path.** The host's own client sends its lobby commands through the same validated path as remote clients (vision O10). The reference's host-only shortcut for kicking bypasses that path.
- Reference behaviour: In the reference, the lobby is part of the same ordered command stream as the match. User-interface controls bound to network values turn each edit into a request to the local or remote server, the server sequences it to every participant, and each participant applies it to its local copy of the match options when the version is newer. The host's controls are the only ones shown, but the server enforces only slot counts, the password and credential checks at join.

### DEC-244 Session join, admission, reconnection and spectators

- Status: Open
- Affects: R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: connecting, password and error pages); R-SIM (`reference/12_simulation_model/06_teams_and_player_commands.md`: team assignment and bot takeover of a departed player's team); DEC-243, DEC-248, DEC-251; `networking.md`.
- Specified behaviour: reference/09 specifies the join, connecting, password and error pages and the outcomes shown to the player: server full, wrong password, incompatible, map missing and kicked. The admission rules below are the reference default.
- Options: A — the reference: admission checks run once, on the server tick after the join; there is no session resumption; late join is allowed, with full-history catch-up; spectators are unsupported in practice; B — admission at the handshake: the authority checks the identity ticket, the build and content fingerprint, the capacity and the password (through a challenge over an encrypted transport) before it sends any state, reconnection by identity resumes the same slot within a grace window, late join uses a snapshot, and spectators are a first-class role with their own capacity; C — B without late join and without spectators, for skirmish only.
- Recommendation: B. The persistent world depends on resumption by identity: AFK is a normal way to play (pillar 2), so a player who reconnects resumes their own settlement and never receives a fresh slot. Checking everything before sending state stops unauthorised clients from receiving any world or match data. Spectating is valuable for skirmish and for community moderators, but it needs its own capacity and its own visibility rules under fog of war.
- Decide by: design phase
- Constraints and lessons:
  1. **Handshake order.** A joining client repeats its join request every 1.0 s until it receives a client id. The server assigns client ids from 0, counting per server lifetime; it announces the newcomer to every participant, then sends the id directly. The client resets its match state and generator seed and replays the history from the first command. When the replay reaches its own announcement it counts as connected, and it then requests a team every 0.1 s until it is assigned one.
  2. **Catch-up time.** History replay runs at most 20 ticks per second faster than real time. Joining a 20-minute match (12,000 ticks) therefore takes about 10 minutes of replay. The connecting page shows the share of history processed so far.
  3. **Team assignment.** A new team takes the first free slot of the six. A local-player request is ignored if the client already owns a local-player team. The requester is removed as "server full" on a single-player server that already has a human team, or when the team count has reached the requested map's player count. Bot-team requests are ignored once the team count has reached the map's player count, so they are always ignored while no map is chosen (a player count of 0). A bot team is owned by the client that requested it, which in practice is the host.
  4. **Admission checks.** On the server tick after the join, each new client is checked once for: its identity, a duplicate identity, server full (the map's player count is not 0, the team count is not 0, and the team count has reached the player count) and a wrong password (exact comparison). The identity status reported by the identity service is re-checked on every tick. A failed check removes the client with a reason. An unknown status (the service is unreachable) never removes anyone, and an identity revoked mid-match removes the player mid-match. Species identity is DEC-248. All admission checks are skipped in single player.
  5. **No session resumption.** A join from a previously removed address registers a new client id; the player replays the whole history and has to obtain a new team. The departed player's team has become a bot team and stays reserved, counting toward capacity, so a rejoin into a full match is refused.
  6. **Late join is never refused.** The server does not check whether the match is running, and the browser lists sessions in progress. If a slot is free, the late joiner's team is created mid-match; otherwise the server-full rule removes it.
  7. **Spectators.** A client joining a session whose client count exceeds the map's player count receives a spectator flag, which it treats as "server full", and it leaves. In the lobby, a seated player can convert to a spectator, which removes their team. The advertised spectator counts are always 0 of 0, and the join-as-spectator path only sets a front-end flag.
  8. **Kick.** Only the host can kick, from the lobby; the removal reason is "kicked".
  9. **Password.** The host sets a password of up to 16 characters. The joiner types it on the password page, and it travels in clear text in the join request; the server compares it exactly. A wrong password returns a "wrong password" removal reason, which shows an error page and leads back to the browser.
  10. **Removal reasons** the front end distinguishes: server full, wrong password, kicked by the host, identity invalid, identity duplicated, identity check failed. Species defines its own enumeration.
  11. **Silent failures.** When the joiner's public address equals the session's public address, the local address and port are used instead (hosting on the same network). A listing without a port makes the join do nothing at all. Every failed join must report a reason to the player.
  12. **Departed player's team.** When a human leaves a match, the team becomes a bot team (reference/12). In the world this is the precedent for the deputy taking over (vision O2), but the settlement stays bound to its owner's identity.
- Reference behaviour: In the reference, joining means connecting to the host's server, receiving a client id and replaying the session's whole command history, which brings in the lobby state and, in a running match, every tick so far. The server admits or removes clients by slot count, password and credential checks, assigns teams to free slots on request, lets the host kick, and has no notion of a returning player.

### DEC-245 Session discovery, the advertised session record and the session browser

- Status: Open
- Affects: R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: the new-or-join, browser, filter and password pages); UI (`architecture/components/ui_framework/pages_and_screen_recipes.md`); DEC-240, DEC-246, DEC-249, DEC-250.
- Specified behaviour: reference/09 specifies the front-end pages that lead to the browser and the join flow. The default browser behaviour is the reference's: one list of local-network and internet sessions, filtered and sorted as described below, in which the player joins a session by choosing its row.
- Options: A — the reference browser over a local-network beacon and an internet directory, with the fixes below (one namespaced key registry, a filter on the has-password flag, no credentials in the record); B — a directory of community world servers (long-lived entries with region, population and a summary of server rules), plus the browser of option A for skirmish; C — platform lobbies and invitations only, with no browser.
- Recommendation: B. Community hosting (O5) needs a browsable directory of long-lived world servers, while skirmish keeps a browser for custom games alongside invitations. In every option, the advertised record carries a protocol version, a build or numeric-model fingerprint and the content hash of the map or world data, and never a credential.
- Decide by: design phase
- Constraints and lessons:
  1. **The advertised record.** A hosting server advertises: a session name (by default the player name, then a fixed default); the game identity and version; the server's start time and a random value, which together form the de-duplication key; its local address and port; the team count (humans and bots); the maximum team count (the requested map's player count, or 1 if the map is not found); the connected human clients, including the host; spectator counts (always 0 of 0); an in-progress flag; the mode; a has-password flag (present only when a password is set); the map checksum; and the public port when known (the local port when port forwarding is configured). A session listing carries no secret; who may join is DEC-248.
  2. **When nothing is advertised.** Two kinds of gate behave differently. While no map is chosen, or while advertising is suppressed for the host, the server skips the tick, and a registration that is already running stays listed. When the mode is unset, or in single player, the registration stops and the listing is withdrawn. A Species session withdraws its listing whenever it becomes unjoinable.
  3. **Propagation.** Changed properties are published at once; unchanged properties are re-sent at the normal period.
  4. **Cadences.** Local-network beacon every 5 s, broadcast to the whole subnet; listing time-to-live 30 s, after which entries that were not refreshed are purged; browser rebuild every 2.0 s, or after 1.0 s while the list is empty once an internet list has arrived; internet list re-requested every 10.0 s.
  5. **List pipeline.** The local-network and internet lists are merged. Internet duplicates of local-network entries (same start time and random value) are dropped, and so are delisted entries. Entries are matched by address. Filters run next, then sorting.
  6. **Filters,** in this order: mode, full, protocol compatibility, missing map, password. The settings store keeps "show incompatible" (which also hides sessions whose map is not installed), "show full" and "show passworded"; the mode filter resets every time the page opens, and a "show custom maps" setting has neither a control nor any effect. The password filter tests a key that sessions never advertise and that collides with another directory field, so it hides nothing. Species uses one namespaced key registry and filters on the advertised has-password flag.
  7. **Sorting.** Compatible sessions with room come first (latest arrival first), then full sessions, then incompatible sessions (in arrival order). There is no sort column for the player to choose; sortable columns and a ping column are recommended.
  8. **Rows.** At most 13 rows are visible, with a scroll bar. Each row shows the session name, a short mode name, the map name (or "unknown map", or "incompatible" with the version), the player count as "(n/m)" with one box per slot (filled for occupied slots, dimmer for bots), and a padlock when a password is set.
  9. **Choosing a row,** first matching rule: incompatible → error page; full → error page; map not installed → error page; password set → password page; otherwise join.
  10. **Manual entries.** Up to 30 entries from the settings store, each giving a host, a port and a name, appear at the top of the list. They carry no version, protocol or map checksum, so choosing one reports "incompatible": manual entries can never be joined. A Species direct-connect entry queries the server for its record before joining.
  11. **Compatibility.** The test uses a protocol-match flag when the directory supplies one, and otherwise equality of version strings. Every build reports the same version string, so incompatible builds look compatible. Species compares a protocol version, a build or numeric-model fingerprint (DEC-240) and the content hash (DEC-246).
  12. **Page bookkeeping.** The browser removes rows by an index that differs from the insertion index, so shrinking the list can remove the wrong focus entry, possibly the Back button. Its scroll bar is created for 10 rows while 13 are shown.
  13. **Silent loss of local discovery.** Local discovery listens on a fixed port. When that port is taken, the client falls back to an ephemeral port, and local discovery stops working without any message. Report the degraded mode to the player.
  14. **Quick match** is part of DEC-249.
- Reference behaviour: In the reference, a hosting server registers its session record with an internet directory and broadcasts it on the local network. The browser merges both lists, removes duplicates and stale entries, filters and sorts them, and joins the chosen session, by way of the password page when a password is set. Player-entered manual servers appear in the same list.

## Terrain runtime

### DEC-246 Terrain runtime model and terrain content identity

- Status: Open
- Affects: TER (`architecture/components/terrain/`: generator, height and normal queries, edge rules); R-MAP (`reference/08_maps_and_level_design/rules_and_conventions.md`, `map_editor_hooks.md`); AST (`architecture/components/asset_pipeline_and_resources.md`: pack files and content hashes); DAT (`architecture/components/data_schemas/`: map definition schema); R-SIM (`reference/12_simulation_model/05_space_routing_and_physics.md`: height and normal queries); DEC-240, DEC-242, DEC-243, DEC-244, DEC-245, DEC-247.
- Specified behaviour: `architecture/components/terrain/` specifies the generator algorithm (per-tile diamond-square with guide grids, a max-composite of tiles, and five flatten operations) and the simulation's height and normal queries. The default runtime model is the reference's: every participant generates the height field at load from the tile parameters of the map definition, and participants identify a map by its map id only.
- Options: A — generate at load, as in the reference; B — bake: the generator runs in the editor and in the content build, the map asset stores the final height grid (binary32, or 16-bit quantised with a scale and an offset) and optionally the normal grid, and the runtime only samples it; C — procedural generation at run time in integer or fixed-point arithmetic, with a counter-based hash generator keyed by (seed, level, x, z), integer or table-driven amplitude laws instead of power and exponential, and explicit edge semantics; D — server-delivered terrain: the authoritative server owns the world height field and delivers it to clients in region chunks, each with a content hash.
- Recommendation: B for skirmish maps, and B with D for the persistent world: baked region chunks, installed with the client or delivered by the server, each identified by its content hash. Generating at load from tile parameters gains nothing, and it makes the terrain depend on floating-point reproducibility (DEC-240). Use C only if the world game needs terrain created at run time, for example a procedurally extended world, and then only in integer arithmetic.
- Decide by: design phase
- Constraints and lessons:
  1. **What must be bit-exact.** Every height sample (binary64 in the reference), the simulation normals, the world size, the column and row counts and the cell size. Simulation code reads them all the time: building heights at load, actor heights every tick, walkability (the water test at height 0.0 and the step and slope thresholds), bounce physics, bot target scoring and weapon impacts. A 1-ulp difference can flip a comparison. The per-tile generator streams must match too, because they determine the heights.
  2. **What need not match:** the render mesh, render normals, colours, water mask, water depth map, waves and clouds, and the presentation-generator draws made during load (colour jitter, shore noise).
  3. **Inputs.** The height field depends only on the map definition (decimal values parsed with binary32 rounding) and on integer seeds. It does not depend on the simulation generator, time, settings or hardware. Any Species runtime model keeps that property.
  4. **Private generators.** Each tile owns a private generator, re-seeded from its tile seed at the start of every generation, so the result does not depend on call history (DEC-242).
  5. **Floating point.** Generation uses binary64 arithmetic, with binary32 rounding of decimal parses, power, exponential, logarithm, square root (in normalisation) and the single-precision absolute value. Reproducing it bit-exactly needs IEEE binary64, no fused multiply-add contraction, no extended precision, evaluation in the order written, and power, exponential and logarithm results that round to the same binary32 value on every platform. Generating all the reference terrains makes about 39.7 million power calls. Of these, 17 lie within one binary64 ulp of a binary32 rounding midpoint, and all 17 are exact squares, reproducible only if power(x, 2) returns the exact square. The 1,120 exponential and 1,120 logarithm calls have none.
  6. **Evaluation order.** Two orders are easy to get wrong: the weights-first bilinear sum of the height sampler, and the sequential additions of the smooth flatten operation. Changing the bilinear order changes practically every terrain, and changing the order of the smooth additions changes every terrain with a smooth area acting above its threshold, 11 of the 57 reference map files (`architecture/components/terrain/` TER-062).
  7. **Index semantics.** Negative indices wrap through unsigned 16-bit arithmetic, reads at the far edge wrap to zero, and the conversion from binary64 to an unsigned 16-bit index truncates. All three are observable in the generated terrain; on the reference maps the edge wrap affects only heights below sea level, so play never sees land at the edge, and the truncating index conversion also underlies the Abductor wander-area restriction (DEC-113). Species defines off-map heights explicitly (a clamp, or an outside height) and keeps every simulation height query on one well-specified bilinear sampler.
  8. **Regeneration.** Applying graphics or other options regenerates the terrain and water from the same definition in the middle of a match. The heights come out the same only because the floating-point environment has not changed. Terrain that the simulation reads must never be regenerated under a different floating-point environment, and with baking it is never regenerated at all.
  9. **Map identity.** Participants agree on a map by its name only. A checksum is computed for listings, but nothing compares it before the match starts, so a participant with a modified map of the same name generates different terrain and diverges without any error. Species puts a content hash (for example SHA-256) of the baked terrain and of the whole map asset into the advertised session record and into the handshake, refuses mismatches, and never identifies a map by name alone.
  10. **Canonical hashing.** A content hash covers a canonical encoding: a fixed element type, a fixed byte order (little-endian) and a fixed traversal (row by row, z outer, x inner), never the in-memory layout. The asset manifest records the hash so that tests can compare golden values.
  11. **Stateless cosmetics.** Cosmetic derivations such as colour jitter and shore noise are stateless functions of position and seed, so that render rebuilds and loading-thread timing cannot change them.
  12. **No presentation work in simulation slices.** The cloud update runs inside a simulation update slice but moves only a cosmetic texture offset, and water animation reads the real-time clock on the render path. Presentation updates never run inside simulation slices.
  13. **Reference terrains are not reproduced.** Species maps are authored new, so bit-equality with the reference generator is not a requirement. The generator specification serves the look of the new editor tool.
- Reference behaviour: In the reference, terrain is never transmitted: every participant regenerates it from its own copy of the map definition when the map loads, and again whenever presentation options are applied. The generator composites 1 to 25 procedural tiles, each with its own seeded generator, and applies flatten areas. The simulation then reads heights and normals through grid queries whose edge behaviour comes from index arithmetic.

### DEC-247 Terrain scale and large-world terrain inputs

- Status: Open
- Affects: TER (`architecture/components/terrain/`); R-MAP (`reference/08_maps_and_level_design/rules_and_conventions.md`); RND (`architecture/components/renderer/world_renderers.md`: terrain rendering and level of detail); CAM (`architecture/components/camera_and_sequences.md`: the strategic zoom of vision O9); R-SIM (`reference/12_simulation_model/05_space_routing_and_physics.md`: spatial grids and route graphs sized from the world extent); DEC-240, DEC-246; `networking.md` (region partition).
- Specified behaviour: The reference library specifies terrain for arena maps whose sizes lie within the figures below; `reference/08_maps_and_level_design/` and `architecture/components/terrain/` state the per-map limits. It specifies no world-scale terrain; the default is one arena-scale height field per map.
- Options: A — one arena-scale height field per region, with neighbouring regions sharing edge samples; B — one continuous world height field, split into fixed-size chunks that align with region boundaries and are delivered by the server and cached by the client; C — regions as separate arena maps joined by transitions, with no continuous terrain.
- Recommendation: B, with chunks aligned to region boundaries, so that a region can move to another server process together with its terrain (vision §5). Keep the reference cell size (median 16 wu), so that crowds and buildings keep the reference scale. Choose coordinate precision under DEC-240: binary64 or fixed point in the simulation, and camera-relative binary32 for rendering.
- Decide by: design phase
- Constraints and lessons (figures over the reference match maps; test, stress and benchmark terrains excluded):
  1. **Grid:** 137 to 334 samples per side, median 190; 18,769 to 111,556 samples per map, median 36,100. The content build rejects a grid of more than 32,768 samples per side, the size up to which the terrain index semantics hold (DEC-968).
  2. **Cell size:** 9 to 27.08 wu, median 16 wu, stored as binary32.
  3. **Extent** (cell size × samples per side): 2,003.61 to 7,020 wu per side, median 3,008 wu; area 4.0 to 49.3 million wu², median 9.05 million wu².
  4. **Area per player slot** (map area ÷ the map's player count): 1.84 to 13.2 million wu², median 3.61 million wu². The median extent is 2,768 wu for 2-player maps, 3,005 wu for 3-player maps and 3,010 wu for 4-player maps.
  5. **Composition:** 1 to 25 generated tiles per map (median 7), and 0 to 6 flatten areas per map.
  6. **Heights:** maximum heights of 175 to 821 wu (median 225 wu). The off-map outside height lies between −30 and −6.93 wu, and is −10 wu on most maps. On a few maps, flatten areas cut below the sea floor, down to −537 wu. Land (height above 0) covers 8 to 68 % of the samples (median 43 %), and every map has sea all along its border (the maximum height along every edge is 0 or below).
  7. **Memory:** a height sample takes 8 bytes as binary64, 4 as binary32 or 2 when quantised to 16 bits. The performance terrain of terrain T26 (334 × 334 samples) holds 0.89 MB of binary64 heights; simulation normals add three components per sample.
  8. **World sizes at reference density** (derived from the median area per player slot and the median cell size): 16 players need about 57.8 million wu², a square of about 7,600 wu (about 475 × 475 samples). 200 players need about 722 million wu², a square of about 26,900 wu (about 1,680 × 1,680 = 2.8 million samples: 22.6 MB as binary64, 5.6 MB quantised to 16 bits). A settlement world needs more room per player than an arena does; these figures scale linearly with the area per player.
  9. **Coordinate precision.** binary32 spacing is about 0.001 wu at 8,192 wu from the origin, 0.004 wu at 32,768 wu, 0.016 wu at 131,072 wu and 0.125 wu at 1,048,576 wu. binary64 spacing at 1,048,576 wu is 2.3 × 10⁻¹⁰ wu. Q32.32 fixed point covers ±2.1 × 10⁹ wu at a resolution of 2.3 × 10⁻¹⁰ wu. Rendering in binary32 needs camera-relative coordinates once the world extends beyond a few tens of thousands of wu.
  10. **Generation cost.** Generating the performance terrain of terrain T26, 25 tiles of 257 × 257 samples, makes 6 527 800 square and diamond calls, each with its powers (TER-240). Baking moves this cost into the content build.
  11. **Spatial structures.** The simulation's actor grid, obstacle grid, surface grid and route graphs are sized from the world extent (reference/12). At world scale they are kept per region or per chunk.
  12. **Strategic zoom.** The strategic zoom level (vision O9) needs a coarse terrain representation, such as levels of detail of the height field, in the same visual style.
- Reference behaviour: In the reference, a map is a single square height field a few thousand wu across, surrounded by sea and enclosed by an outside height, and sized for 2 to 4 players. Simulation grids and route graphs cover the whole map, and the camera never needs coordinates beyond the map's extent.

## Services

### DEC-248 Player identity and entitlement

- Status: Open
- Affects: PLT (`architecture/components/platform_layer.md`); BLD (`architecture/components/build_tooling_and_distribution/`: packaging, distribution and the trial product); R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: the reference library specifies no credential-entry page); DEC-244, DEC-249, DEC-250, DEC-251; `networking.md`.
- Specified behaviour: The reference library specifies no identity, entitlement or trial gating; a player is identified only by the display name in the settings store. Until the design phase decides, no entitlement check applies.
- Options: A — a platform account service: storefront accounts, session tickets that the server validates, and the trial as a separate platform product; B — an own Species account service with token-based authentication, optionally linked to platform accounts; C — identities local to each community server, with no central service; D — A for entitlement, plus a small Species identity service that accepts the platform's proof of ownership and issues short-lived signed tokens, which any server, the companion interface and the world database use as the stable identity.
- Recommendation: D. Community servers (O5) must check who a player is without holding any publisher secret, and the persistent world (O1, O2) and the settlement-status and orders interface (O6) need an identity that stays stable across platforms, reinstalls and name changes. Tokens bound to one server and checked with a public key give both, while the platform entitlement still decides ownership and the trial. If no Species service may run at launch, use A, keyed on the platform account id, and keep the token format as the planned upgrade.
- Decide by: design phase
- Constraints and lessons:
  1. **Never publish credentials.** A session record is public, so it carries no credential and no other secret (DEC-245).
  2. **Never send a secret in clear text.** The session password travels in clear text in the join request. Species uses an encrypted transport and checks passwords by challenge, never storing or logging them in clear.
  3. **A purchase is not a session.** Species keys sign-in on a stable account id, never on a copy of the game, and states each server's duplicate sign-in policy explicitly: refuse the second sign-in, or replace the first.
  4. **Validation timing.** The identity status is checked asynchronously after the join and re-checked on every tick. An unknown status (the service is unreachable) never removes a player, and a revocation removes the player mid-match. Species chooses explicitly between availability (play continues while the service is down) and enforcement, and never removes a player mid-battle because of a service-side change without a grace rule.
  5. **Trial through the distribution platform.** Trial and full access are separated by the platform entitlement (a trial product), never by in-game lists of permitted maps and modes that a service supplies at run time.
  6. **Hosts are untrusted.** A community server (O5) verifies a player's identity without receiving any reusable credential or publisher secret. Tickets are bound to one server (audience), expire after a short time and are not replayable.
  7. **One stable identity.** Settlement ownership in the persistent world (DEC-251), the protection rules for AFK players (O2), moderation and bans on community servers (vision §6 item 10) and the settlement-status and orders interface (O6) all key on one stable account id that survives display-name changes and reinstalls.
  8. **Beyond the game client.** The settlement-status and orders interface (O6) must later accept clients other than the game client, so it uses a standard token-based scheme, not a ticket that only the game client can produce.
  9. **Server-side validation on every server build.** Identity validation is available in every server build, the dedicated-server build included; a client-only library is not enough.
  10. **Local and offline play.** Decide whether local-network and solo sessions require an identity. The reference skips every admission check in single player.
  11. **Decide the service set once.** The choice of platform account and storefront services drives transport, lobbies, entitlements and achievements together, and it is an open business decision.
- Reference behaviour: The reference has no entitlement model that Species keeps; Species uses platform entitlements.

### DEC-249 Directory, rendezvous, relay and matchmaking services

- Status: Open
- Affects: PLT (`architecture/components/platform_layer.md`: network services); R-META (`reference/09_front_end_and_match_flow/screen_flow_and_match_setup.md`: browser and quick-match entry points); DEC-245, DEC-248; `networking.md`.
- Specified behaviour: The reference library specifies no online service. The reference default is a local-network beacon plus an internet directory, with public-address identification and connection setup through a rendezvous service, and no relay. Quick match joins the first compatible session that has room, and no menu leads to it.
- Options: A — the lobbies, matchmaking and relays of the chosen platform service set; B — an own directory and rendezvous-and-relay service operated by the Species team; C — community-run directories (any operator can run one, and clients keep a configurable list), plus the local-network beacon and direct connect; D — a combination: A for skirmish invitations and matchmaking, and B or C for the directory of world servers.
- Recommendation: D. Community-hosted world servers (O5) need a directory that lists servers independently of any storefront, while skirmish invitations and matchmaking are cheapest on a platform service. Keep a versioned local-network beacon that carries the content hash, and direct connect, for local play and private servers. Specify every field of every service message, including the fields a service adds on its own. A world-server record needs at least the fields of the reference session record (DEC-245) without the credential, plus a region and capacity, so that players can choose a server.
- Decide by: design phase
- Constraints and lessons:
  1. **Specify the service side.** Session discovery is a design-phase service (DEC-245), with no message of the day and no trial limits. A rendezvous service tells a socket its public address and port and relays connection requests so that both sides open their address-translation mappings. Species owns a documented protocol for each service, including every field a service adds to a listing, or uses a platform service whose behaviour is documented.
  2. **Endpoints are configuration.** The client has a development directory endpoint built into it. Species keeps service endpoints in configuration, with separate development and production environments.
  3. **Cadences.** Public-address identification every 10 s while browsing or hosting; connection requests through the rendezvous service every 1.0 s until the server answers; local-network beacon every 5 s; listing time-to-live 30 s; internet list re-requested every 10.0 s.
  4. **No relay fallback.** Address translation is traversed by hole punching only, so a session behind restrictive address translation cannot be joined. Species needs a relay fallback, on the platform or its own, for both skirmish and world servers.
  5. **Security.** Never broadcast credentials (DEC-248). Reject unknown or malformed service messages and never terminate on them. Use an encrypted transport.
  6. **Quick match.** It joins the first protocol-compatible session that has room, with no latency, region or skill criteria. Species chooses between skill, region or latency matchmaking on the platform, or none; it applies to skirmish only, because players choose their world server.
  7. **Graceful degradation.** When an internet service is unavailable, play degrades to local-network discovery and direct connect, and the browser says so.
  8. **Stable listing keys.** The reference matches listings by address. Species keys every listing on a server id issued at registration.
- Reference behaviour: In the reference, a client contacts the directory and the rendezvous service at start-up. A hosting server registers its session record with the directory and broadcasts it on the local network. A joining client asks the rendezvous service to open a path to the host before sending its join requests, and the browser presents the merged results.

### DEC-250 Persisted data inventory and client-local storage

- Status: Open
- Affects: R-META (`reference/09_front_end_and_match_flow/options_localisation_and_hooks.md`: options, achievement and leaderboard hooks); R-SIM (`reference/12_simulation_model/`: the command-stream replay hook); PLT (`architecture/components/platform_layer.md`: settings store and profile folder); DAT (`architecture/components/data_schemas/`: preferences schema); INP (`architecture/components/input/`: control-scheme bindings); DBG (`architecture/components/diagnostics_test_and_performance/`: replay); DEC-245, DEC-251.

No match, lobby or session state is saved. Achievements and replays are hooks only.

- Recommendation: B. - Decide by: design phase
- Constraints and lessons:
  1. **What the reference saves,** in the client-local settings store: the player name; the session name; the server and client network ports; the port-forwarding flag; the browser filter settings ("show incompatible", "show full" and "show passworded", plus a "show custom maps" setting that has no control); up to 30 manual server entries, each giving a host, a port and a name; the control-scheme bindings, in a bindings file of their own; and the graphics and other options listed in reference/09. Applying some of these options regenerates the terrain and water from the map definition (DEC-246).
  2. **What the reference does not save:** the browser's mode filter, which resets every time; lobby state; match state; and any session state, so a departed player cannot resume (DEC-244).
  3. **Achievements.** Per-player achievement masks are exchanged in the lobby every 60 s; the platform award call is a stub, and where achievement progress is stored is part of the achievement hook in reference/09.
  4. **Replays.** The command history of a match is a complete record (lobby commands, start, and every tick's commands), so replay recording is a hook on the command log. Replays depend on the determinism scope of DEC-240 and on the recorded generator seed (DEC-242).
  5. **Simulation never reads client settings.** A terrain detail setting is read by terrain code but forced to one value, so it cannot change simulation heights. Species keeps every client setting out of simulation inputs.
  6. **Decimal settings** are parsed with the platform-independent parser of DEC-241.
  7. **Text form until this entry is decided.** The settings file is UTF-8 without a byte-order mark, one line per entry, comment or blank line, with line feeds as line endings; an entry is `<key> = <value>`, and comment and blank lines keep their place on save. The file carries no schema version and is never migrated (`architecture/components/data_schemas/config_input_and_strings.md` DAT-196, `reference/09_front_end_and_match_flow/options_localisation_and_hooks.md` R-META-409); the typed and lossless rules of DEC-800 apply whatever this entry decides.
- Reference behaviour: In the reference, the client keeps one settings store of named values in the profile folder, alongside a separate control-bindings file. The front end and the network layer read and write it; nothing about a session, a lobby or a match outlives the process.

### DEC-251 World-state persistence, schema migration and rollback

- Status: Open
- Affects: R-SIM (`reference/12_simulation_model/02_match_lifecycle_and_state_reset.md`: per-match state ownership and reset); DAT (`architecture/components/data_schemas/`: schema versioning); PLT (`architecture/components/platform_layer.md`); DBG (`architecture/components/diagnostics_test_and_performance/`); DEC-240, DEC-242, DEC-246, DEC-248, DEC-250; `networking.md`; `process_tick_and_roadmap.md`.
- Specified behaviour: The reference library specifies no persistence of simulation state. A match world exists only in memory, from load to match end, and per-match state is created at match start and reset at match end (reference/12). The default is no world persistence.
- Options: A — a single world save file, written periodically as a snapshot; B — a transactional database per world, with one schema for every host (an embedded engine for integrated and small community servers, a server database for larger ones), records keyed by region, consistent periodic snapshots and a journal of completed transactions; C — an event-sourced world: a command log plus periodic snapshots, with state rebuilt by replaying the log.
- Recommendation: B. The vision rules out A (O1: world state in a database rather than a single save file). C turns every patch into a determinism risk, because rebuilding state by replay requires bit-exactness across builds (DEC-240). B gives region-keyed records that can move with a region to another server process, transactions for consistency after a crash, and a schema that migrates forward. The integrated server (O10) uses the same schema in an embedded engine, so that a world can move from an integrated host to a dedicated server.
- Decide by: design phase
- Constraints and lessons:
  1. **Database from day one** (vision O1): world state lives in a database, partitioned by region, so that regions can later move to separate server processes.
  2. **The world freezes during downtime** (vision O4): there is no catch-up, and world time is server uptime. Persist an integer world tick counter, and store every timer (shield periods, protection caps, deputy schedules) in world ticks, never as wall-clock time.
  3. **Status and orders are server state** (vision O6): settlement status and deputy orders are read from and written to persisted server state through the authenticated interface (DEC-248).
  4. **Portable world data** (vision O10): an integrated world can move to a dedicated server (a Windows build under O21, or another host that a later ADR decides), so every stored value uses an exact encoding with a defined byte order (DEC-240 item 10).
  5. **Migration, backups and rollback** (vision §6 item 7): forward migrations with a schema version per record set; a server refuses to open a world written by a newer schema; scheduled backups; a stated maximum loss window after a crash (the time since the last completed transaction).
  6. **Rollback granularity.** Rollback is also a moderation tool for community hosts (vision §6 item 1). Decide whether it applies to a whole world or a single region: interactions across regions, such as an attack, make a single-region rollback inconsistent.
  7. **No hidden state.** In the reference, state that survives between matches outside the match world is a known integrity failure. The persistent equivalent: no process-global state survives outside the persisted record, and everything not persisted can be derived at load.
  8. **Content identity.** World records refer to terrain chunks and data assets by content hash (DEC-246), so a patch that changes content is detected at load.
  9. **Generator state.** Persist the world seed, and the stream positions if sequential streams are kept (with counter-based streams, nothing more; DEC-242).
  10. **One record for both models** (vision O3): a settlement's persisted state is the same record whether the full simulation or the abstract economy model last advanced it.
  11. **Skirmish** (vision O8) needs no persistence beyond results and statistics (the results and achievement hooks of reference/09).
- Reference behaviour: In the reference, a match's world is built from the map definition at match start, lives only in memory, and is reset at match end. Joining players rebuild it by replaying the command history. No match, lobby or session state is written to storage.
