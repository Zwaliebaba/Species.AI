# R3b review: implementability of the engine baseline

> Reviewer: R3b (Phase 5, R3 Adoptability, engine half) · Date: 2026-10-18 · Scope: the 12 engine components under `design_next/architecture/components/`, read with `design_next/ADR/` (README index and technology baseline, and the ADRs the components cite) and `AGENTS.md` as the implementer's rules · ORIG not read · Paths in the tables are relative to `design_next/` unless they start with `AGENTS.md` or `.github/`.

## Summary

Question asked: could an implementer start each component today under `AGENTS.md`, with interfaces sketched in its style, data contracts defined, threading stated, runnable acceptance tests, numeric budgets on named hardware, Accepted technology decisions, acyclic dependencies that respect R9, and defined failure responses; and can the solution, the first projects and CI be created without a decision nobody has made?

Overall: the baseline is unusually complete. Every component has a §2 sketch in `AGENTS.md` naming, a threading contract, a failure table and a concrete §7 test table. Many tests carry exact vectors: terrain's binary64 vector sets, the UI's layout values, the audio gains. The gaps are concentrated in four places:

- **The seams between components.** Nothing specifies how a non-renderer component creates GPU resources. Several pairs of components depend on each other, so they cannot be split into two libraries as written. The presentation snapshot and the pass context are named but never defined.
- **The tools solution.** The tools solution cannot share project files with the game's solution under the `$(SolutionDir)` rule.
- **Proposed ADRs.** Nine Proposed ADRs sit on the critical path. Each names a complete default, so none blocks work, but none says when or on what evidence it is confirmed.
- **Measurement.** No reference machine is named. There are no golden-image tolerances, and no tool runs the boundary lint checks, so the performance, golden-image and boundary tests cannot yet decide pass or fail.

### Components with blocking gaps

- **Build tooling and distribution (tools solution):** finding 1 blocks the content build tool and everything it builds (cookers, schema generator, map validation).
- **Asset pipeline and resources (run-time residency), with the renderer, the UI glyph cache and the VFX pools:** finding 2. Nothing specifies how these create GPU resources, and the creation order is circular.

Every other component could start today, or after a Medium gap is closed (see the per-component verdicts at the end).

### Severity rationale for Proposed ADRs

The ADR README says a Proposed record names the default the team proceeds with. All 18 Proposed records do, so none blocks implementation. A Proposed ADR on the critical path of the first playable is rated Medium: the default is clear, but work built on it may need rework, and no record says when or on what evidence it is confirmed. Proposed ADRs off that path are rated Low.

## The build story, end to end

This walk-through creates the repository's first code from `build_tooling_and_distribution.md`, `AGENTS.md` and the ADRs.

1. **The game's solution and its first library.** This can be done today. The toolchain pins, compiler and linker settings, configurations, output path, `pch.h`, `packages.config` restore and `FXCompile` rules are all stated (BLD-027 to BLD-042, BLD-121; ADR-051, ADR-054, ADR-055). One decision is missing: the solution name, the project list and the edges are left to the first implementer (finding 3). AGENTS.md §2 expects that decision then, but nothing proposes it, and findings 14 to 17 show the layering is not obvious.
2. **Test projects.** These can be done today (ADR-069: `<Project>Tests`, `SuiteSmoke`, `vstest.console.exe`, the `Requirement` attribute). Fuzz projects need finding 8.
3. **CI.** The committed `build.yml` runs as is: its guards pass an empty tree, and each step starts gating when its input lands. BLD table 4.9-A omits the generated-schema step (finding 5). Several checks that the components rely on have no checker (finding 9). `CheckProjectFiles.py` must be written from scattered rules (finding 62), and its package rule would fail the tools solution (finding 12).
4. **The tools solution and the content build tool.** These are blocked. Shared project files cannot work under the `$(SolutionDir)` rule (finding 1). The DirectXTex dependency is not recorded with its licence and package id (finding 11). How the glTF validator runs on Windows is not recorded (finding 13).
5. **Generated schema code.** This is partly blocked. The decision is Proposed (finding 7), and the record contradicts itself (finding 6). How CI obtains the generator, how the generator bootstraps, and where each schema's code goes are unstated (finding 4).
6. **First content and the first client run.** This needs the content build tool (step 4), a pack byte layout (finding 18), and a GPU-resource seam between the asset cache and the renderer (finding 2).
