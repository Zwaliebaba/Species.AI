## Known conflict: ADR-0063 against DEC-099

**What the reference does** (my ORIG ranges):
- The language list offers every language table present, whatever its coverage.
- A missing key shows the key text, so the three stub languages (about 7–9 % coverage) show raw ids for most of the interface.
- At start-up the language is chosen in this order: the stored preference, the OS locale's language, English, the first file present. If none loads, start-up stops with a fatal error.

**What the document specifies:**
- DEC-099's rule (Resolved): per-key fallback to `en-GB`, and only complete languages are offered, with `ref.meta.lang.offer_coverage` set to 100 % (R-META-463, R-META-464).
- The start-up order (R-META-465): stored setting, then the OS preferred languages with ADR-0063's tag fallback, then `en-GB`, then the first offered language.
- §5 item 5 states the reference behaviour and cites both records.

**Recommendation: change ADR-0063.** Replace its release rule ("…or when the release sign-off accepts the listed fallback keys explicitly") with a reference to DEC-099. My reasons:
1. Which languages players are offered is product policy, not engine technology. The ADR index says ADRs cover technology only.
2. DEC-099 is Resolved and comes from the corpus's own recommendation to complete or remove partial languages.
3. The engine mechanism is the same under both rules: per-key fallback, a per-edition coverage report, and a language list built from that report.
4. A sign-off list puts back the mixed-language screens that DEC-099 removes.

If the owner wants some tolerance at patch time (new keys before their translations arrive), that belongs in a DEC-099 amendment with a bounded, signed-off list per patch, not in the ADR.

**Minor alignment.** ADR-0063's selection rule starts from the OS preferred languages. DEC-099 starts from the stored preference and ends with "the first language present". ADR-0063 should add both steps, which R-META-465 already specifies.
