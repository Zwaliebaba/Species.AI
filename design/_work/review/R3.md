Implementability gaps: **High 0, Medium 5, Low 15** (20 in total). There are 8 cross-document inconsistencies.

Overall, both documents are of very high fidelity. I checked the AI priority formulas (§5.2–§5.6), the decision-loop timers (§6.1, re-derived tick by tick), the difficulty table (§13), the building capture rules (§3.7, §4.5, §5.1, §5.4, §6.2, §8.1, §8.3) and the level-file grammars. They match the code almost everywhere, down to tie-breaking and NaN behaviour.

Three most serious findings:
1. **07 §7.4, the selection-gate hazard, is overstated** (sampled line 824, Partly correct). The doc says that after the AI places a unit, officer promotion stays blocked until a Goto officer calls `SetOrders`. That list of selection-clearing calls is incomplete. The AI's own Darwinian power-up placements (`RunPowerup` → `Task::TargetBooster/Subversion/HotFeet/Rage` → `Task::SwitchTo`) also call `SelectUnit(-1,-1,-1)` (`code/taskmanager.cpp:482-507`, `:816-977`). So do `Officer::SetOrders` in formation mode (`code/worldobject/officer.cpp:1375`) and `TaskManager::AdvanceTasks` (`code/taskmanager.cpp:1463`). The predicted stall and slot-leak effect (B13/B24, 07-U1) is therefore weaker than written.
2. **03 gives two timings that disagree with other documents and with the code.**
   - Spawn-network latency is stated as "exactly 1.0 game second per link" (§4.1, §14). The code takes 11 increments for the first hop and 10 for each later one, and the hand-off order within a tick can shorten a hop (`code/worldobject/spawnpoint.cpp:429-450`). Doc 05 §3.4 already has this right.
   - The Blitzkrieg "base under attack" throttle is stated as 20 s (§8.1, §14). The 20.0 timer is decremented by 0.1 only once per recount, so the real throttle is about 200 recounts, roughly 210 s (`code/worldobject/multiwiniazone.cpp:279,286`). Doc 01 already has this right.
3. **03 marks two features as live that are not, or not fully.**
   - Armour → GunTurret conversion is listed as a live turret source (sampled line 900). In Multiwinia it cannot happen: `m_awaitingDeployment` is set only in the `!Multiplayer()` input branch (`code/location_input.cpp:1046-1053`), and the other setter is commented out (`code/location.cpp:3915-3965`). It is [B:LEGACY].
   - The Assault solar-panel knock-out rule misses a case. `m_startingTeam` is an `int` that defaults to −1, and the test is `!= 255` (`code/worldobject/generator.cpp:633,673,738-743`). A panel that starts neutral is therefore also knocked out on its first capture. This is latent in shipped data, because all Assault panels start team-owned.
