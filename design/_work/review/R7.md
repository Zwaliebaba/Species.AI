Implementability gaps: **High 1, Medium 5, Low 9** (15 in total). Cross-document inconsistencies: **5**.

**Test: can a heightmap be reproduced from a level file?** Mostly yes. I followed doc 23 and got exactly the doc's values for `mp_koth_2P_1`:

- the derived values of §16.2 (n, comp, highest, heightFactor, posXi/posZi);
- all ten RNG and write events of §16.3;
- the four probe heights of §16.4;
- the grid digest `bb4397625e5006a1`.

Across all 69 shipped landscape files, 58 grid digests match §18 exactly, and grid size, min, max and land % match on all 69.

**Three most serious findings**

1. **23 §18: 11 of the 69 golden digests do not follow the code (High).** All 11 maps contain smooth (type 3) flatten areas that act on terrain above their threshold. The digests in §18 were evidently made by a port that adds the four neighbours together first and then adds the centre term: `c + (((n0+n1)+n2)+n3)`. The code (`code/landscape.cpp:434-441`) and the doc's own §8 text add them one by one, starting from the centre: `h = c; h += n0; h += n1; h += n2; h += n3`. When I re-ran with the neighbours-first order, all 11 reproduced the doc's values. So an implementation that faithfully follows the code would fail the doc's own conformance procedure (§17.5 step 4) on these maps. The code-faithful digests are in §4, G1.
2. **23 §3: the bilinear `GetValue` formula leaves the multiplication order open (Medium), and the order changes every digest.** The code computes each weight first, `w11 = (1−fx)(1−fy)`, then multiplies `v·w11` (`code/lib/2d_surface_map.cpp:88-97`). If the doc's formula `v(x1,y1)·(1−fx)(1−fy)` is evaluated left to right, every map hashes differently: `mp_koth_2P_1` becomes `18ef1d7ee15d8c7f` instead of `bb4397625e5006a1`. Since the doc says bit-exactness is required, it must state the order.
3. **26 §4.6: the damage-flicker idiom is described wrongly (Medium), and four cross-document errors were found:**
   - In §4.6 only Spider uses the darkening blend. Officer, Squadie, Shaman, SporeGenerator, Tank, Armour, Triffid and AntHill use additive `ONE, ONE`, mostly with a three-way choice of axis. Harvester and Engineer have no flicker at all.
   - Doc 24 gives the explosion triangle cap as ≤ 501; the code gives 502.
   - Doc 08 says "later tiles win" where tiles overlap; the code takes the per-sample maximum.
   - Doc 26 says the Christmas light colours are "multiplied"; the code replaces them.
   - Doc 22 lists `Landscape::SphereHit` as a simulation consumer; it has no caller at all.

Overall, docs 23 and 24 are unusually precise. Every render-pass state I spot-checked matched the code: 18 passes, the baseline and the shader table.
