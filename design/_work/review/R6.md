Overall the three documents are unusually precise: the main loop, slice partitioning, `GameTimer` semantics (all 11 speed-request durations re-simulated exactly), the Directory/packed-int wire grammar (the 35-byte SYNCHRONISE example is byte-exact), the ALIVE payload, the server resend window, the sync-check algorithm, MT19937/LCG definitions, the seed derivation and the double-precision countdown tick counts all check out against code.

Three most serious findings:

1. **22 §14.11 L13 (Difficulty-preference desync, rated "medium, reachable") is not reachable.** Every level load constructs a `LevelFile`, whose constructor calls `App::UpdateDifficultyFromPreferences()`, which forces `m_difficultyLevel = 0` (`code/level_file.cpp:1484-1488`, `code/app.cpp:625-637`, called from `code/location.cpp:419-421`) before anything in the simulation reads it; the Other-Options Apply value (`code/interface/prefs_other_window.cpp:37-43`) is therefore overwritten, and Apply is ignored in a match (`m_locationId != -1`). The row also misstates `EntityBlueprint::GetStat`: only `StatSpeed` (and not for SpaceInvader) is scaled (`code/worldobject/entity.cpp:105-117`). The error propagates to §14.6 (ParseInstantUnits row), §14.12 and §14.13, and contradicts 21 §5.9 step 10.
2. **22 §14.12 / L20 ("High"): the `Armour::SetDirectOrders` static hazard is unreachable** in an unmodified baseline peer: NEXTWEAPON/PREVWEAPON are the only paths to it (`code/network/clienttoserver.cpp:2754-2786`) and neither has a live sender — the only `RequestNextWeapon` call sits inside a block comment (`code/location_input.cpp:1054-1062`); `RequestPreviousWeapon` has no caller. §5.4 rows 25–26 present them as live commands and the "defined but never sent" list omits them. The `s_numMultiwiniaZones` half of L20 is correct.
3. **MasterSpawnPoint is mis-tagged and its static mis-described.** 20 §5.3 tags `MasterSpawnPoint::s_masterSpawnPointId` [B:LEGACY] and "set when a master spawn point initialises"; 22 §14.12 repeats "overwritten when a master spawn point initialises". In code the id is written on **every** `MasterSpawnPoint::Advance` (`code/worldobject/spawnpoint.cpp:548-550`), the type is not blocked (`code/worldobject/building.cpp:771-812`) and `SpawnPointMaster` appears in 34 of 57 `data/levels/mp_*.txt`; 21 §2.8 (#73) and 03 correctly say [B:FULL].

Also notable (Medium gap): the server keeps only the latest ALIVE per client per tick (`code/network/server.cpp:887-897, 1078`), so OR-accumulated one-shot flags (clicks) in an earlier ALIVE of the same tick are silently discarded; no document states this consequence, and 22 N11 recommends the pattern unqualified.
