**Three most serious findings**

1. **06 §3.5 L423, task-slot re-sort (Medium).** `TaskManager::Advance` loops from the end with `i--`. After a swap, the same Running task is compared again at `i−1`, so in one tick it passes **every** adjacent Started task. It does not "drift left one slot per tick". Slot order decides the 1–9 key mapping, so the doc's rule gives different key mappings. `code/taskmanager.cpp:1487-1500`.
2. **09 §1.2.3 L153 and §11.8 L2269: gamepad control help is said to be live (Medium, cross-document).** In fact `ControlHelpSystem::Render` returns at once whenever `g_app->Multiplayer()` is true, which is every Multiwinia game. `Advance` also has the inverted test that 06 describes. 06 §10.1 is right and 09 is wrong. `code/control_help.cpp:929-932, 455-456`.
3. **06 §1.5 L178/L181, object-under-cursor resolution (Medium).** The kinds are not compared by "nearest along the ray". The metric is the **screen-space distance** between the ray-hit point and the object's projected centre. `GetBuildingId` returns the **first** RadarDish or GunTurret in list order with range 0, and an Armour hit is forced to range² = 0.001. This decides what a click selects. `code/location.cpp:4065-4072, 4136-4142, 4196-4211`.

Other notable findings:
- 08 §2.2/§3.5 say a missing thumbnail falls back to `default.bmp`. In fact nothing is drawn; 09 §3.5 is right.
- 06 §1.4 gives the wrong reason why NEXTWEAPON/PREVWEAPON are never sent. As a result, the desync that 22 L1722 lists for them can never happen.
- 06 X30: the missing `compass_empty.bmp` is practically never requested. If it were, `Resource::GetTexture` would abort the game with a fatal `AppReleaseAssert`. That answers 06-U12.
